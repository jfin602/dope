2. "Okay I created our basic structure"

## Target everyday experience

**Greenfield brainstorming with no code:** The developer may say "Let's plan a 2D tower-defense game with PixiJS." Chat should immediately offer a useful provisional approach (for example, a small playable vertical slice, renderer/game-loop separation, enemy movement, tower placement, waves/resources, UI/tests), explain one or two tradeoffs and ask at most a targeted consequential question when helpful. No existing file, generated Roadmap, canonical Architecture or Physical Map is required to *think*. Label design recommendations as proposals/assumptions, not as verified repository facts. A library name such as `pixi.js` is a technology reference in ordinary conversation, not automatically evidence of a missing `pixi.js` project file. The normal answer need not match an exact canned list of features or fixed headings.

**After the developer changes their project:** When told "I created our basic structure", Dope should inspect the **currently attached workspace** using existing project-safe read-only list/search/read capabilities, verify that the state has actually changed, identify current paths/configuration and explain how this affects the plan. It must not merely repeat "no files attached". If nothing is attached, multiple workspace roots are ambiguous, the project cannot be safely read, or evidence is stale/omitted, say **exactly which condition is verified** and offer a supported recovery path; never claim an inspection that did not happen. The model should see current evidence at the *next relevant turn*, not only a stale prior snapshot. Preserve source hashes, bounded tokens and project isolation.

**Ongoing conversation:** Follow the developer's ideas and confirmed decisions across turns, avoid identical missing-evidence reports, make engineering suggestions and help narrow the first feature. Distinguish source facts, inference, user-stated decisions and design options. The developer can ask a question or brainstorm without triggering a structured JSON action, planning approval, graph mutation or hidden model call.

**Formal planning when requested:** Existing schema-validated implementation-plan proposals, Roadmap projection and Planning Bridge are still available for an intentional request. Idea exploration and an ordinary response are not failed plan envelopes. Do not force unstructured discussion into `planOnly`, create a Roadmap draft because the user says "let's plan", or automatically publish Markdown/WorkItems/prompt stacks. Make the transition from conversational discussion to formally reviewable plan explicit and source/revision-safe; use the current Chat/model/approval owners.

## Product and security boundaries

- **Existing saved ChatPanel only.** Preserve user-selected left/right/center/bottom placement, per-turn provider selection, saved conversation, project-root attachment, leases, restart/restore, cancellation and distinct Chat vs Work authority. Never build a second conversational system or mandatory planning wizard.
- **Project facts need evidence; design recommendations do not need existing code.** Never claim a file/module/installed version was inspected unless current project evidence entered that turn. Do not treat absent Architecture/Physical Map as proof that the source tree or project does not exist.
- **Relevant, automatic inspection is bounded and read-only.** Prefer a tiny current top-level orientation, then on-demand root listing/manifest lookup, targeted source reads and revisions when the user says they created/changed files or asks what exists. Reuse `ChatProjectGrounder` and `ChatContextComposer`; respect project-relative paths, symlink/traversal denies, `.dope` privacy, byte/token budgets, cancellation and source freshness. No ambient full-repository ingestion or unprompted background model loops.
- **No model/provider change by default.** The developer may qualify using explicitly selected, actually loaded Q4_K_M at measured 32768 context; do not assume that capacity globally or switch providers/enable hosted egress silently. Record actual provider/model/context and token limitations for live runs.
- **Human ownership of the game.** Do not use the live tower-defense project for destructive validation, automatic project setup, forced file edits, canonical Roadmap writes, Git mutations, deployment or AI Work runs. Security/path-negative tests and destructive failure cases use disposable project copies with their own IDs and evidence.
- **Do not weaken approvals.** Source hash/conflict checks, preview/reject/undo, authored prompt immutability, architecture adoption, Work grants and candidate promotion still apply. Phase 11 and historical corrections retain their separate qualification truth.
- **Repair Dope without depending on a healthy Dope runtime.** Documentation and product defects may be addressed through the separate Dope repository using normal source-control safeguards; no forced use of Dope's own broken feature.

## Iterative workflow and evidence protocol

1. **Use the real project normally.** The owner develops the tower-defense game at their own pace. Never require them to rebuild, reset or supply screenshots of files Dope can already inspect through authorized project tools.
2. **Capture a reproducible friction observation.** Exact human request, prior-turn context, visible model reply, Dope/Git source and version, which project was attached, Auto-context refs/diagnostics and expected developer outcome. Classify owner's direct observation separately from independent browser replay and source hypothesis.
3. **Investigate the smallest existing seam.** Compare what ChatBackend grounded/composed/sent with what Q4 actually returned; verify that model constraints don't turn design hypotheses into falsely missing code facts. Diagnose before proposing an implementation.
4. **Authorize a bounded fix only after review.** Prefer a single, manually supervised vertical slice and direct real-browser retest, not another nested correction-stack series. Use focused deterministic tests for permissions, source truth and lifecycle, then live user task qualification on the same project (read-only where feasible) or safe disposable copy.
5. **Record exact result and continue building.** Preserve failures and follow-on decisions; Dope-product qualification and game-development progress are separate ledgers. An observed passing turn qualifies only its actual task/scope, not all of Phase 11.

The duplicated headings are an observation, **not** a proven hardcoded template.

Previous `c11-conversational-planning` P8 and `c11-cp-recovery` P5 were **NOT GREEN** despite source-bound passing aggregates; later manual Checkpoint One work remained uncommitted and was NOT GREEN at its stopping point. These records must remain immutable historical evidence. The new initiative does not retroactively qualify them, pre-approve further code work, or require the game to reproduce old fixtures.

## Target everyday experience

**Greenfield brainstorming with no code:** The developer may say "Let's plan a 2D tower-defense game with PixiJS." Chat should immediately offer a useful provisional approach (for example, a small playable vertical slice, renderer/game-loop separation, enemy movement, tower placement, waves/resources, UI/tests), explain one or two tradeoffs and ask at most a targeted consequential question when helpful. No existing file, generated Roadmap, canonical Architecture or Physical Map is required to *think*. Label design recommendations as proposals/assumptions, not as verified repository facts. A library name such as `pixi.js` is a technology reference in ordinary conversation, not automatically evidence of a missing `pixi.js` project file. The normal answer need not match an exact canned list of features or fixed headings.

**After the developer changes their project:** When told "I created our basic structure", Dope should inspect the **currently attached workspace** using existing project-safe read-only list/search/read capabilities, verify that the state has actually changed, identify current paths/configuration and explain how this affects the plan. It must not merely repeat "no files attached". If nothing is attached, multiple workspace roots are ambiguous, the project cannot be safely read, or evidence is stale/omitted, say **exactly which condition is verified** and offer a supported recovery path; never claim an inspection that did not happen. The model should see current evidence at the *next relevant turn*, not only a stale prior snapshot. Preserve source hashes, bounded tokens and project isolation.

**Ongoing conversation:** Follow the developer's ideas and confirmed decisions across turns, avoid identical missing-evidence reports, make engineering suggestions and help narrow the first feature. Distinguish source facts, inference, user-stated decisions and design options. The developer can ask a question or brainstorm without triggering a structured JSON action, planning approval, graph mutation or hidden model call.

**Formal planning when requested:** Existing schema-validated implementation-plan proposals, Roadmap projection and Planning Bridge are still available for an intentional request. Idea exploration and an ordinary response are not failed plan envelopes. Do not force unstructured discussion into `planOnly`, create a Roadmap draft because the user says "let's plan", or automatically publish Markdown/WorkItems/prompt stacks. Make the transition from conversational discussion to formally reviewable plan explicit and source/revision-safe; use the current Chat/model/approval owners.

- **Human ownership of the game.** Do not use the live tower-defense project for destructive validation, automatic project setup, forced file edits, canonical Roadmap writes, Git mutations, deployment or AI Work runs. Security/path-negative tests and destructive failure cases use disposable project copies with their own IDs and evidence.
- **Do not weaken approvals.** Source hash/conflict checks, preview/reject/undo, authored prompt immutability, architecture adoption, Work grants and candidate promotion still apply. Phase 11 and historical corrections retain their separate qualification truth.
- **Repair Dope without depending on a healthy Dope runtime.** Documentation and product defects may be addressed through the separate Dope repository using normal source-control safeguards; no forced use of Dope's own broken feature.

### Intended experience and response brevity

Default straightforward brainstorming should favor a **single concise recommendation**, one short ordered path, a clear first playable/working milestone and, if useful, one consequential question. Approximately **100–170 words** is a *soft guidance target*, not a maximum, tokenizer filter or hard validation; depth must expand for technical requests, safety context, actual source complexity and the user's requested detail. Do not duplicate a feature inventory and an implementation sequence that say the same thing. Measure actual generated output tokens, duration and usefulness on the selected model; faster generation is a hypothesis, not a qualification claim. Do not force a standard numbered template, a "confirmed/missing" report, a formal JSON plan envelope or an extra model review pass onto ordinary Chat.

After enough real project discussion, the assistant should **check authoritative Roadmap state** (not infer from missing Chat context, missing files, or an absent Architecture/Physical Map). When there is no canonical Roadmap, no accepted creation intent and no conflicting Greenfield draft, it may proactively offer to build a *noncanonical* strategic draft using the decisions already made. Example for the owner's PixiJS game, as a **proposal, not current project fact**: Foundation; Map and Enemies; Towers and Combat; Economy and Progression; MVP Qualification and Polish. Each phase must have meaningful objectives/checkpoints with first-playable milestones and dependencies; **five is not a required phase count or product-specific template**. Ask at a useful decision point, not reflexively in every reply. If canonical Roadmap or a draft exists, offer **Open/Continue/Review**, never duplicate or overwrite.

### Single authority path for button and conversational confirmation

An offer should have **typed, ephemeral-to-the-appropriate-owner proposal identity**: canonical project ID/root, saved Chat ID, proposer/owner, Roadmap project ID and expected owner revision, pending/draft/source basis and one-use proposal/confirmation token. The backend rereads `RoadmapStore` and Greenfield state immediately before accepting; deny stale, foreign, conflicting, expired, double-submitted, canceled or unowned offers. Model output/text is untrusted; **the model may suggest a tool action but cannot authorize the action itself**.

The existing ChatPanel displays a restrained, accessible primary action (e.g. **Generate Draft Roadmap**), a neutral **Not now** action and a concise description of what will happen. The same validation/approval service handles a button click and a clear developer reply such as **"Yes, create the roadmap"** to the specific current pending offer. An isolated "yes", quoted transcript, model message, stale Chat response or ambiguous overlapping proposal is **not consent**. Approved offer = permission to **start generating a reviewable draft**, not approval to publish its contents. A separate review/approval remains mandatory to accept the generated draft and, later, to publish linked Markdown/canonical Roadmap. Reject/Not now leaves state unchanged and does not nag repeatedly.

**Proposed internal capability names** (not present product APIs): `proposeRoadmapCreation` (read/check+offer), `generateRoadmapDraft` (single validated, project-bound approval then generation), and `openRoadmap` (frontend navigation to the existing canvas). Prefer one narrow Chat-to-planning capability interface owned by existing `ChatBackend` / `RoadmapGreenfield` / `RoadmapStore`; these can be methods or typed actions, **not arbitrary model-controlled shell, filesystem, network, provider tools or Work grants**. No duplicate Chat/Plan/Roadmap store, no direct model writes, no changing Chat selected-model policy or implicit hosted data egress. If a user explicitly asks for the feature, make the same offer/approval flow available without requiring a precise phrase.

### Draft generation, progress and editor focus

`RoadmapGreenfield` already provides saved draft ownership, reviewed implementation-plan projection and separate linked Markdown publication. However, `projectImplementationPlan` creates strategic phases by dependency levels (not guaranteed to match the discussed phase outline), and Greenfield `previewEditSequence` currently permits only 2–3 actions. **G3 therefore needs a bounded full-strategic-draft preview/validation route within the existing owner**, accepting a complete proposal with appropriately capped phase/checkpoint/dependency counts and stable basis; do not emit five sequential dummy clicks or force the developer into one- or three-node-at-a-time assembly. The model proposes a coherent outline, Dope validates schema, meaningfully reviewable content, project/revision/source freshness and graph integrity before it can be displayed as an editable *noncanonical* draft. Never accept the model's own claims of approval as authority. Preserve the separately approved canonical Markdown file creation and existing prompt/Work immutability.

After the developer authorizes generation, emit lightweight **truthful application-driven progress** through the existing Chat event/controller/presentation seam. Suggested stages (not percentages, not claims about private reasoning): checking current Roadmap and project, generation authorized, waiting for selected model, generating outline, validating structure, preparing editor, ready/error/canceled. Only display a stage when its corresponding application boundary has actually occurred. During a long model inference maintain responsive "generating" status, ability to cancel and clear failure/retry recovery; **no second model inference solely to narrate work, no fabricated tokens or intermediate steps**. Avoid copying private project text into progress messages. The existing planning-progress event has only waiting/validating and needs compatible scoped extension if necessary; keep old consumers stable.

Once a **valid** draft is ready, invoke the existing frontend `dope.roadmap.open` command, focus/reveal the single main-editor Roadmap canvas (not create a second tab/panel system), load/refresh the current project-bound draft and fit its phases/checkpoints into view. Preserve Chat's chosen left/right/center/bottom placement, its saved conversation, active model and writer lease. Don't navigate before ready or on rejection; if navigation fails, keep the accepted draft accessible with a recoverable **Open Roadmap** action. Opening a draft is **not** canonical publication. A changed project, owner, source or revision blocks action with visible recovery instead of showing a phantom/foreign Roadmap.

Roadmap intent is based on **developer request + saved Chat context**, not the presence of the literal word "draft" in assistant prose. "Let's make a roadmap" or equivalent clear creation request must start the project-bound **reviewable proposal** path; ambiguous bare "Roadmap" with no clear context may receive one concise clarification. Do not call the model again by default. The tool remains responsible for authoritative `RoadmapStore` + `RoadmapGreenfield` eligibility, ID/revision/lease/token checks. No silent model/tool command authorizes canonical writes.

Extraction prioritizes explicit Phase N headings, named Roadmap/Implementation Order sections, then a single unambiguous ordered sequence. Ignore feature inventories, explanatory lists, quoted text, unrelated enumerations and duplicated competing lists; select a source deterministically or surface ambiguity for user review instead of guessing. For the owner's G1 answer containing both Core Components and Implementation Order, extract the implementation order **once**. Preserve ordered titles and actual supported checkpoint bullets. When the parser path is used, **Follow Interactive / unloaded model is not a creation blocker**, because no inference is performed. If optional expansion is selected, resolve a permitted current model based on user selection and trustworthy actual source-message provenance, recheck model availability before consuming the offer, and report supported recovery if unavailable. Consume approved offers atomically only after non-destructive prerequisites or make recoverable failure/renewal explicit without duplicate effects.

**No speculative schedule policy:** Roadmap generation must not add phase week ranges, completion estimates, calendar deadlines or forecast durations unless the developer explicitly supplied them as constraints. New unsourced date labels and phrases such as "(Weeks 1–2)" are removed from extracted draft headings while original Chat prose stays byte-identical. Existing user-authored dates in requirements and project documents remain as source context, not an inferred estimate. This rule covers ordinary suggestions and parsed Roadmap presentation, not all engineering conversation.

**Requirements fidelity and project truth:** Use developer-stated requirements as a separately visible coverage checklist with source message references.

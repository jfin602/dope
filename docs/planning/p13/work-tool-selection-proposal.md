# Work tool selection and reusable groups — unified Work authorization design

**Original approval:** 2026-11-24. **Owner amendment:** 2026-11-25 (`/docs-review` → `/docs-apply`). **Status:** OWNER-APPROVED DESIGN / DOCUMENTATION APPLIED ONLY; implementation and qualification not included. **Scope:** single user-facing Work authorization, complete safely brokerable Pi tool selection, and internal grant enforcement. No source code, prompt-stack Run, version, Roadmap status or historical evidence change follows from this document.

## Problem and current boundary

Current GitHub source already provides **Tools for this Work**, but Work UI also renders a separate **Review project execution grant** list of abstract effect kinds, and some Work entry paths still require **Accept project execution grant**. Those names are not Pi tools. The five built-in Pi Work wrappers currently listed by `WORK_TOOL_CATALOG` are real model-callable tools; the static list alone must not become a permanent ceiling on future qualified registered Pi tools. This duplicated authorization UI is confusing and unnecessary.

The existing `ExecutionGrant` is a fixed effect ceiling. Its parser rejects changes to that ceiling: candidate workspace reads, writes, bounded processes, tests/builds, project create/modify, and Git inspection are allowed; delete/rename, Git writes/history, network, secrets, private state, outside-root, destructive, system, and package administration are denied. Local Pi Work currently exposes `read_file`, `list_files`, `edit_file`, `run_command`, and `read_command_output` through Dope's broker. The chooser authorizes exact tool exposure for a run, while the fixed effect ceiling remains an **internal security limit**, not a second user approval. Selecting a tool never converts a denied effect into an allowed one.

## Approved experience

**2026-11-25 amendment (supersedes the November 24 UI wording):** **Tools for this Work is the sole user-facing execution-tool authorization surface.** After reviewing the project, selected Pi agent/model, exact effective tool set, and validation restrictions, the developer authorizes ordinary Work once by choosing **Start Work**. The backend creates its bound `ExecutionGrant` automatically as a result of that explicit action. Remove the separate **Review project execution grant** disclosure and **Accept project execution grant** checkbox from all Work start/retry/resume surfaces. Preserve separate dirty-source acceptance, hosted-project-data consent, sensitive MCP per-call approval, and later candidate Accept/Reject: these are different safety decisions, not duplicate tool permission switches.

1. Display **Tools for this Work** as the only tool permission chooser in each Work start/restart path. Show a compact selected-group summary, individual tool checklist, exact effective tools and disabled/unavailable reasons alongside task, project, model and required validation. The single **Start Work** approval replaces both the blanket checkbox and separate fixed grant-review UI; never present abstract effect classifications as model-callable tools.
2. Offer built-in groups initially: **Inspect** (`read_file`, `list_files`), **Edit** (`edit_file`), and **Commands** (`run_command`, `read_command_output`). The ordinary Work preset can select all eligible built-ins for compatibility; a smaller-model preset can begin with Inspect and add only needed tools. Group labels organize choices; they do not introduce new execution authority. If command execution is unavailable for the task, Commands is unavailable. `read_command_output` is useful only with `run_command` and must not be exposed alone.
3. Let the owner create, rename, duplicate, and delete reusable custom groups by explicitly checking tool identities. In a Work draft, allow group selection plus individual overrides; an explicit individual denial wins over a group inclusion. Show the final list and why any requested tool is unavailable. No wildcard, “all future tools,” or silent membership expansion.
4. At **Start Work**, approve the exact task, source/project basis, model/provider, resolved callable tool identities, and their stated restrictions **in one user action**. Issue the existing immutable Work `ExecutionGrant` and bound tool-selection record internally; do not require another execution grant checkbox, approval card or allow/deny capability matrix. The model sees only checked supported tools; the broker independently rejects unchecked, forged and stale tool calls. Dope-owned required validation, candidate review, promotion and History remain separate.
5. Group definitions are reusable across projects, but the selected groups and overrides for a Work task are project/task scoped. A saved default selection may be project local; it never auto-approves a new Work run. Editing a reusable group does not modify a running or previously approved run. A retry/resume must recheck the frozen selection and current provider/tool availability; material drift requires a new review.

## Authority and provider rules

**Trusted full-catalog discovery:** Enumerate every actual Pi tool registered for the selected agent and classify each as eligible for Dope-brokered Work, temporarily unavailable (with a concrete reason), or unsafe/unsupported by the Work authority boundary. Every eligible tool must be individually selectable rather than hidden behind a hard-coded five-item UI. Registration metadata must describe stable tool identity, schema/catalog revision, supported provider/project, effect requirements and invocation dependencies. This includes new qualified extension/MCP tools when Dope has a broker and policy capable of enforcing every call; a standalone Pi tool or plugin is **not** an allowed Work tool simply because it exists. Show disabled entries when meaningful, but never enable raw Pi file/shell/network bypasses. A newly registered tool is not silently selected by a saved group, preset or existing grant. A checked `run_command` remains constrained to approved validation commands, not arbitrary shell access.

**Grant and UI roles:** The developer manages tools only in **Tools for this Work**. The existing `ExecutionGrant`, effect maximum and audit fields stay internal Dope enforcement/evidence records created from the explicit Start Work authorization. Effect kinds (`workspace-read`, `project-modify`, `git-write`, `network`, etc.) are not callable tools and must not appear as additional permission checkboxes. The user may inspect short explanations of actual tool restrictions, but no second configurable project-execution grant exists.

The effective tool set is the intersection of: trusted tool catalog, provider capability, project enablement, selected groups and overrides, existing grant/effect policy, and any narrower task restrictions. A denial at any layer wins. Check the selection at model registration **and** each broker invocation so a hidden or forged request cannot execute. Bind the approved snapshot to stable tool IDs, schema/catalog revisions, provider/model, project, task, and grant revision; fail closed on an unknown, removed, changed, or stale tool. Keep safe tool-call outcomes in the originating Work transcript and saved History without storing credentials, protected arguments, or source bodies.

Local Pi is the first implementation target because Dope registers and brokers its tools. Other providers may have different enforcement capabilities. If a provider cannot honor the exact list and broker gate, show that limitation and do not present its tools as individually controllable; do not silently switch provider or claim parity. The tool selector must also cover Work started from a WorkItem, Prompt Stack, phase runner, and retries, rather than only the New Work composer.

External MCP tools have a separate boundary under [ADR 0058](../../decisions/0058-optional-external-mcp-integration.md) and its [compatibility contract](external-mcp-compat-contract.md): installation/configuration is global, project activation defaults off, and each invocation needs Dope authorization. A custom group can reference a qualified MCP tool only when its exact server/tool identity is available and approved for that project. Selecting a group never installs or activates a server, supplies credentials, approves a call, or permits a direct live effect. Initial read-only MCP observation and its single-call approval remain distinct from built-in Work tools.

This design preserves the current OS sandbox, isolated ExecutionWorkspace, command allowlist, path/source checks, candidate validation and promotion, and separate owner review. Future tools needing currently denied effects require a separate explicit policy decision and security qualification; group creation alone cannot expand the fixed grant.

## Acceptance criteria for implementation

- One Work tool permission interface, **Tools for this Work**; **Start Work** is its single explicit authorization. No duplicate grant-review disclosure or acceptance checkbox appears on any start or restart surface.
- All actually registered Pi tools eligible for Dope-brokered Work are individually selectable; unavailable/unbrokered tools are not executable. No fixed five-entry UI ceiling, phantom capability tool, or silent exposure from new extensions or MCP registrations.
- The model receives only selected tools, with independent broker rejection for deselected/forged/stale calls; tool IDs, schemas, provider, project, task and grant revision remain bound through recovery.
- Existing denied effects stay denied; arbitrary process/network/secrets access, project-path escapes, Git writes/history and unreviewed MCP calls remain blocked. Hosted provider limitations and any required hosted-data consent are accurately presented.
- Saved custom groups/defaults, command-tool prerequisites, dirty-source review, mandatory validation, CandidateDelta Accept/Reject, checkpoint and History preserve their existing contracts.
- Regression tests include `test/unit/work-tool-selection.test.ts`, `work-selection.test.ts`, `pi-work-execution.test.ts`, `work-mcp-authorization.test.ts`, `local-tool-broker-*.test.ts` and actual Pi Work UI qualification. Record negative security evidence rather than treating removed UI as a passed security gate.

## Owner decisions

- The November 25 decision supersedes only the previous **user-visible grant management** requirement. The fixed internal effect ceiling and `ExecutionGrant` are not removed or broadened. Extra grants, approvals or privileges cannot be inferred from checking a tool.
- Tools eligible for this Work must be surfaced from trusted live registration and a Dope-brokerable enforcement contract; unsupported raw Pi/plugin tools are not implicitly authorized.

- Reusable custom group definitions are machine-local to the Dope installation. A project may save a default *selection*, but definitions do not travel with the project.
- The initial implementation keeps the existing fixed effect ceiling while making tool exposure selectable. A specific tool needing a currently denied effect requires a separate bounded policy decision and security qualification.
- A group edit affects only future approvals. An in-progress Work run keeps its frozen list or is deliberately stopped and restarted.

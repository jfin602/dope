# Phase 13 — Task-Anchored Documentation Routing contract

> **2026-11-07 documentation proposal workflow update:** `/docs-review` stages a pending proposal. Its card offers **Accept**, **Reject** and **Revise Proposal**. Accept invokes guarded application and applied-only History directly. Revise Proposal selects the existing proposal in the Chat composer and starts a new `/docs-review` only when the owner submits instructions. The selected proposal's ID, revision, current proposed bytes, base/source identities and original review intent are carried in protected review state. A failed or stale revision leaves the last valid card unchanged. The former `/docs-apply` command is withdrawn from the current user workflow. This update does not qualify P8 or any Phase 13 Gate; historical prompts and reports remain dated evidence.

**Approved design:** 2026-11-05. **Status:** forward requirements only; no Phase 13 implementation or qualification by this document. **Baseline:** `0.13.0`. **Lifecycle authority:** [ADR 0051](../../decisions/0051-roadmap-work-evidence-lifecycle.md) and the [Phase 13 lifecycle contract](roadmap-work-lifecycle-contract.md). **Documentation authority:** [ADR 0041](../../decisions/0041-planning-documentation-workflow-and-applied-history.md) and its [application/Work-reference contract](../p12/documentation-workflow-contract.md). **Qualification authority:** [ADR 0040](../../decisions/0040-phase-gate-roadmap-domain.md).

## Outcome and ownership

The Phase 13 journey is **Roadmap → applicable project documentation → reviewed Prompt Stacks → authorized Work → verified Roadmap progress**. The agent reads instructions and relevant requirements to perform the original coding task. Reading, planning and prompt generation are observable activities, never evidence of implemented behavior or a qualified Criterion.

This contract refines the documentation handoff in the existing lifecycle. It adds no second Roadmap, task, plan, document, progress or History owner. Repository files own written requirements; ADR 0041's reviewed application owner alone publishes Dope-proposed document changes and History projects only verified applied effects. Schema-2 Roadmap owns Phase/Gate/Criterion identity and qualification. Planning Bridge owns its PlanningMap/PlannedTransformation/WorkItem links and approvals. Prompt Stack/AgentTask/AgentRun, grants, candidate review, validation and History retain their existing owners. The Task Contract below is a **checked, durable projection of those records** for one execution basis, not a competing database or a model-authored replacement objective.

## AGENTS.md-first routing

For a project that has an applicable `AGENTS.md`, inspect the root file when present and any nested `AGENTS.md` governing the intended working paths **before** task-specific documentation exploration or coding. Recheck nested applicability if the approved working set moves into another subtree. Treat these files as concise routes to coding practices, documentation locations, applicability and project-specific instructions. Apply nested instructions only within their declared path scope. Follow the project's actual conventions when `AGENTS.md` is absent; do not require Dope's own filenames or layout in other projects. A file's imperative prose, recency or link order cannot override the accepted task, a higher-priority instruction, an owner decision or an executable grant. Surface material conflicts for review.

The runtime must establish **how** applicable instructions reached this Work run: native Pi loading, a Dope-brokered read, or another verified existing mechanism. Record the applicable path/scope and observed source identity when available. Do not append a second copy if the same instructions are already present in the run context. Keep any Dope-supplied routing note short; read bodies only as needed under safe tools. If a required AGENTS file is missing, unreadable, stale or contradictory, report the specific limitation and continue only within a safe, known task scope.

**Current-source constraint, not an implementation claim:** the pinned Pi worker currently supplies `getAgentsFiles: []` through an isolated resource loader; Pi Work exposes brokered `read_file`/`list_files` and approved candidate test/build tools, but no Work-wide text-search tool. Its exact page read can continue by offset and source hash; path-only reads retain a clipped legacy prefix. Phase 13 implementation must inspect and verify the actual runtime path before relying on native instruction loading, avoid duplicate injection, and use the existing safe read/list/page mechanism or a separately reviewed narrow repair. Do not enable arbitrary Pi resource discovery or host access to obtain AGENTS files.

## Task Contract at handoff and recovery

Project the following fields from their existing owners when preparing Work and before each authorized run. Bind the projection to project/root/worktree identity and an immutable task/preparation basis; retain its source record IDs, revisions or hashes and mark absent facts `unknown` rather than inventing them.

| Field | Existing authority and required meaning |
| --- | --- |
| Original objective | Developer's accepted request and the frozen executable prompt/task snapshot; retain its wording and intent through retrieval and recovery. |
| Roadmap linkage | Accepted schema-2 Phase/Gate/Criterion IDs, revision, approved coverage and linked Markdown/source basis where applicable; unresolved or direct-Work linkage stays explicit. |
| Current work and plan | Approved Planning Bridge WorkItem/transformations/dependencies, current AgentTask or stack step, bounded execution plan and next action; direct Work need not fabricate a WorkItem. |
| Allowed scope and source basis | Project/candidate/worktree identity, accepted source and dirty-tree facts, applicable instruction/document identities, grant/lease, tool and candidate restrictions. |
| Acceptance and verification | Criterion expected results where linked, task-specific acceptance checks, approved validation targets, required manual/browser/native observations and evidence gaps. |
| Execution and recovery | Existing task/run/checkpoint IDs, completed versus pending steps, actual tool/edit/test results, candidate review/promotion state, interruption reason and safe next action. |

The model can summarize a plan or suggest a change, but only the relevant owner can change an accepted task basis. A documentation read cannot silently replace the original objective, insert a new task, widen scope or grant, mark a step done or renew a stale approval. A **material** change to an accepted WorkItem requirement or source basis follows ADR 0041's distinct reviewed preparation and fresh task-bound grant; pointer updates, read receipts and nonsemantic edits alone do not trigger replacement. Preserve immutable executed prompts, earlier runs, decisions and historical NOT GREEN evidence.

At a handoff or recovery boundary, reconstruct this projection from authoritative records before inviting model continuation. Compare the reconstructed basis with the last known projection and current source. If an owner record or source identity cannot be verified, present the missing fact and pause only the affected action; do not assert recovered memory, replay a mutation or silently resume Run. The projection is compact enough to fit the selected local model's usable context, with detailed evidence and documents available by bounded references rather than copied bodies.

## Task-driven, bounded documentation use

1. Start from the Task Contract's objective, working paths, Criterion links and current execution step. Follow applicable AGENTS routing, then cheap explicit task/document links or known metadata. ADR 0041 references remain optional and include path, section if known, role, reason for applicability and truthful known/unknown version.
2. Select the narrowest relevant file/section or available safe search justified by a concrete question. Read through authorized project/candidate tools, using pagination and source identity for late sections. Work's current list/read tools do not imply a text-search capability. Distinguish current requirements from drafts, examples, historical reports and unverified claims. A linked file does not become authoritative merely because the agent read it.
3. Retain a small finding with its path/section/source identity, applicability, resolved question and any unresolved conflict. Use that finding for the active implementation step. Reopen a file only when the source changed, the prior excerpt was insufficient, a new question requires another section, or a verification check needs current bytes.
4. Return to coding, an approved test/review step or a specific blocker. Research may continue when a real unresolved dependency requires it; there is no arbitrary total-file, depth or token cutoff that prevents necessary authorized investigation.

No automatic full-repository documentation scan, mandatory body prefill, recursive link traversal, per-Work-turn model call, document summarizer loop or unchanged notice injection is required. Explicit `/docs-review` discovery retains its separate ADR 0041 behavior. When no optional task-specific reference applies, add no optional-document notice/body or extra Dope model call; applicable AGENTS instructions are ordinary project-instruction routing and their cost is measured separately. Provider-specific read receipts may be unavailable; offered reference, observed read and requirement-following must remain distinct, with unknown recorded as unknown.

### Loop and relevance guard

Within the existing task/run provenance, track a bounded navigation trail keyed by canonical project-relative path, section or byte range, observed source hash and the question being answered. Detect circular references when a link returns to an already explored question/source; detect repeated unchanged reads when the same range/hash yields no new fact; detect excessive documentation-only activity when successive reads or model turns do not resolve an open task question, change the plan, produce an implementation effect or expose a new blocker. These are **signals for a task-aware decision**, not fixed hard stops or evidence of failure by themselves.

On a signal, offer the known finding and ask the agent to name the missing fact, choose a different bounded section, resume the active execution step, or report a concrete blocker. Legitimate new questions, changed source and deeper necessary research remain possible under the same tool/grant checks. Do not create a hidden retry loop or silently skip required documentation. Record read activity as read activity, never implementation progress.

## Context, interruption and source discipline

Keep the Task Contract and verified finding/checkpoint references outside model conversation memory, attached to their existing owner records. Before compaction or a fresh authorized retry, retain the original objective, acceptance criteria, next step, verified findings and source identities, unresolved questions, actual tool/edit/test outcomes and pending approvals in compact, checkable form. Reuse a verified finding instead of rereading unchanged content merely to rebuild context. A summary is an unverified note until reconciled with owner/tool/source evidence; never manufacture a result from a truncated transcript.

Current Pi Work uses a fresh in-memory one-shot session per start/capacity retry, an isolated resource loader and native compaction with a Dope guard; overflow retry is cancelled because a Work tool may already have changed the candidate. Phase 13 must preserve those facts and test any new retention/recovery behavior against source before relying on it. Cancellation, restart and interruption preserve candidate bytes and owner records; resumption needs the existing explicit Run/grant, lease, source and candidate-review checks. Do not use compaction as a substitute for durable task state or grant authority. If safe reconstruction fails, show a targeted recovery action and no false continuation claim.

## Roadmap evidence boundary

ADR 0051 and ADR 0040 alone govern Criterion qualification. AGENTS/doc reads, findings, plans, authored prompts, model success, WorkItem completion, tool exit zero and checkpoint commits cannot award GREEN. Only attributable, current and sufficient implementation/verification evidence, associated through the existing checked source-bound receipt path and reviewed where required, can contribute. Candidate-only results require accepted-source applicability after promotion. A failed or missing verification remains visible; no model self-awarded GREEN or automatic Phase closeout. Documentation application History records actual document changes only, not product progress.

## Phase 13 acceptance and qualification

Add the following deterministic and live cases to the existing P13 lifecycle acceptance. Treat them as forward qualification requirements for a separately authorized implementation, **not** as a rewrite of immutable `p13/P*.txt` prompts or an assertion that their current stack already covers these cases. Before Run, assess the stack against this contract and separately author/approve any necessary bounded correction or qualification work under normal workflow.

The expanded [c13-doc-routing correction route](../../tasks/c13-doc-routing/README.md) supplies Task Contract/AGENTS/bounded reading/recovery as P1–P4, source-checked Docs proposal/application/History and protected `/docs-review` as P5–P7, and a real-browser manual complete documentation-pipeline P8 before original p13 P9. Current Docs qualification must exercise card Accept, Reject and Revise Proposal, including preserved drafts, successive revisions, stale failures and exact final application. Its F1 remains the full-journey check before p13 P13. Its authoring is not a Run or qualification receipt; the original p13 gates and owner Phase disposition remain independently required.

- **Routing and relevance:** root AGENTS-first execution; nested AGENTS in and out of scope; already-loaded instructions not duplicated; absent AGENTS; relevant versus irrelevant documents; missing or conflicting current requirements; explicit role/supersession handling.
- **Scale and loop behavior:** large documentation tree without automatic corpus ingestion; circular links; repeated identical section/hash; a legitimate new question or changed source still retrievable; long/late sections reached with safe paged reads; measured documentation bytes, calls and time against a no-reference control.
- **Context and recovery:** small supported local-model context; compaction with original task/plan/criteria and verified findings intact; failed compaction/overflow; cancellation, restart, source change and authorized fresh retry with truthful state reconstruction, no duplicate reading/notice, no grant or candidate bypass.
- **Real coding and evidence:** start from a reviewed Roadmap/Planning Bridge/Work basis, read the applicable instruction and late requirement, author/review a Prompt Stack, perform actual source changes and approved tests in Work, review/promote the candidate as required, then inspect attributable current Criterion receipts and derived Roadmap state. Verify task objective and acceptance criteria survived. Run negatives where reading/planning/prompt generation/model success or a passing candidate-only test leave GREEN unavailable. Exercise manual browser and owner-native evidence required by ADR 0051 independently.

Record exact product source, task/owner IDs, selected model and measured context, applicable instruction/document hashes, offered and observed reads, actual source/test effects, candidate disposition, receipt IDs and remaining gaps. A successful explanation of documentation without source implementation and verification is **NOT GREEN**. Historical reports remain unchanged; the owner makes any final Phase disposition only after the complete current-source workflow passes.

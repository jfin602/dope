## Decision

Keep the owner-requested **compact, visually faithful Roadmap element preview inside Chat** in place of dominant raw proposal JSON. Embed **View in Roadmap** in that card. Opening it reveals the *same validated proposal* provisionally in the **existing Roadmap center editor**, focuses its affected Phase/Gate, and does not change canonical Roadmap/Markdown bytes. **Accept** applies only through the existing validated backend review; the provisional treatment becomes ordinary canonical content *only after a confirmed successful apply*. **Reject** removes the provisional canvas treatment without a write. Historical Chat activity remains truthfully labelled accepted/rejected/stale. No second mock store, writer, agent or approval authority.

The mini-card is an intentionally compact projection of the actual reviewed before/after entities; the Roadmap canvas is an optional richer inspection, not a second step required for approval. Raw model JSON may remain in explicit diagnostics/Copy JSON, never as the ordinary default review.

**2026-10-31 P3-B forward invocation boundary (documentation only):** In the later protected-Skills integration, the **AI-generated schema-2 edit-proposal entry** used in step 1 requires a Dope-verified, turn-scoped `/roadmap` invocation. A selected Phase/Gate or model-produced proposal envelope alone is not authorization. Read-only Chat remains freeform/selection-based. The skill does not approve or apply: existing proposal/lease/revision/source checks and the exact same Chat Accept/Reject, mini-card and optional canvas overlay remain the only applicable review path. Manual editors, greenfield Roadmap creation and linked document reconciliation keep their own existing authority. This requirement starts only after separate P3-B implementation and Chrome qualification; H1–H3 and P2 historical results are not upgraded by this design.

**Separate input context versus output preview (2026-11-01):** [Roadmap Element picker](roadmap-element-context-picker.md) starts from Chat **Add Context** to select existing authoritative records for the *next user prompt*, inserting a user-triggered protected `/roadmap` prefix with trusted invocation. This document's **View in Roadmap** instead displays a *pending AI output proposal* for inspection. Neither selection nor a transient preview approves an edit. Picker is later work after Skills qualification and does not change H1–H3 status.

### Minimal user journey

1. An explicit conversational edit yields a **typed, source/revision-bound pending proposal** through the existing `gateProposal`/planning preview path. Freeform discussion and read-only answers do **not** create the card.
2. In Chat, show affected Phase/Gate/criterion, action type, relevant old/new fields, proposed-entity marker, and **Proposed · Not applied**. For several actions, show a clear bounded summary and count with inspectable detail; do not silently discard actions. Keep **Accept**, **Reject**, and **View in Roadmap**.
3. **Manual View in Roadmap** checks current project, saved Chat ownership, proposal identity, owner revision and linked-source state before opening/focusing the center editor. The conditional automatic preview uses the same validation and existing canvas projection only when the Roadmap tab is already active. Focus the affected existing item, or the parent Phase for a new Gate/criterion. Render the complete proposal in place: new entities have clearly distinct provisional rows, edits highlight changed fields, deletions keep a visible proposed-removal ghost, moves/reorders/dependency changes disclose their before/after placement. Do not make unapproved changes appear Green or accepted. Support bounded multi-action proposals atomically, without an intermediate half-applied state.
4. **Accept** in Chat (first implementation stage) invokes exactly the preexisting `decidePlanningProposal(..., true)` approval. Backend revalidates project/lease/owner/source/revision/token, mutates only through Roadmap or linked Markdown authority and returns actual revision/effect. Canvas then removes the ghost, reloads canonical data and focuses the applied item; a short visual transition is optional and must never delay writes. On rejection `decidePlanningProposal(..., false)` removes the ghost without a canonical write. A failed or stale apply clears/disables the misleading preview, preserves current canonical data and offers review/refresh guidance.
5. The Roadmap canvas is **inspection-only for the first qualified delivery**. Do not introduce competing canvas Accept/Reject controls just to finish this feature. If later added, they must dispatch the *same* backend proposal ID, lease and acceptance decision and be separately qualified. Keep the original docked Chat open; user should be able to return to it without resetting selections.

## Owner refinement — inline card and active-tab-only automatic preview (2026-11-01)

The proposal's compact, exact, validated mini-card belongs **inside its originating assistant final answer**, immediately above the response footer and at the full available assistant-content width. Do not also show a “Roadmap change” activity row or a second standalone Chat message. A decided/rejected/invalidated proposal remains in the same location as an inert compact history card under [ADR 0045](../../decisions/0045-roadmap-proposal-lifecycle-and-publication.md); retain backend audit events.

**Automatic preview is conditional on the current center-editor tab at the instant a genuinely new, validated, still-reviewable proposal arrives:**

| Center editor at proposal arrival | Preview and focus behavior |
| --- | --- |
| Existing Roadmap tab is **active** | Automatically perform the *preview/locate/highlight* portion of **View in Roadmap** in that existing tab, showing the exact same provisional projection; do **not** open/switch tabs or steal keyboard focus from Chat/composer. |
| Roadmap tab exists but another editor tab is active | No automatic navigation, preview activation, tab switch or focus change. |
| Roadmap tab is closed | Do not open it, change editor selection or move keyboard focus. |
| Saved/replayed/history proposal or terminal status update | No automatic preview; render the appropriate card/history state only. |

The card's **View in Roadmap** button stays available for every supported *valid pending* proposal regardless of whether it has already been automatically previewed, and remains the explicit way to open/focus the Roadmap from an inactive or closed state. It is not a second approval mechanism. The auto-preview uses the same project/Chat/proposal/lease/source/revision validations, transient presentation bridge and affected-entity navigation as the manual action; it bypasses **only** the explicit tab activation/focus request. Never auto-apply, publish Markdown, or claim Gate/Phase Green.

Drive automatic preview from the **new authoritative proposal-arrival event**, keyed by stable proposal identity and originating turn, not React rerenders, activity replay, historical restoration, reopening or status changes. Recheck that Roadmap remains the active editor before dispatching any delayed navigation; if the user changes tabs meanwhile, abort. A later switch *to* Roadmap must not belatedly trigger the earlier proposal. Multiple pending proposals retain independent inline cards and correct IDs; only the newly arriving valid proposal may replace a currently shown transient overlay while Roadmap is active. When a proposal becomes stale/decided/project-mismatched, clear its provisional overlay truthfully without jumping the user elsewhere. Use the current camera/selection APIs, avoid forced Fit All or persistent viewport writes, and do not delay model streaming or file operations.

### 2026-11-03 exception — continuous updates, one-time navigation

The arrival rule above controls **automatic tab navigation/initial locating**, not the cadence of visual updates. A current authorized Planning turn may publish a **validated, incomplete native-stage projection** before its final reviewable proposal exists. If the Roadmap is already the active center tab, the first eligible partial snapshot may enable the one-time provisional overlay; each subsequent validated stage sequence for that **same** proposal updates the same in-place ghosts without a second arrival, card, focus transfer, Fit All or camera jump. A manual user decision to open Roadmap mid-generation may show the latest server-validated provisional state; this is not an automatic delayed switch. Inactive/closed tabs remain untouched. Historical mode suppresses updates. Only a complete backend-validated decision-ready proposal produces the one compact final Chat card and enabled Apply/Reject controls; incomplete generation remains read-only. Invalid/stale/cancelled identity removes live ghosts and all approval authority. [ADR 0047](../../decisions/0047-native-roadmap-authoring-and-automatic-sync.md) and the [native authoring contract](native-roadmap-authoring-contract.md) govern event sequence, error handling, performance and qualification. This is a documentation clarification, not a new Chat owner or implemented behavior.

## One authoritative preview; transport only what the UI needs

Current inspected `ChatPlanningProposal` exposes `id`, `chatId`, `messageId`, `ownerId`, `revision`, `changedIds`, action label and a textual `summary`. Current `ProjectPlanningActions.preview()` already produces a validated `next` snapshot, changed IDs and an approval token; `ChatBackend` retains the pending request/token and, for linked source-owned fields, a separate `GateDocumentPatch`.

The Chat mini-card and canvas **must not parse** `summary`, raw model JSON or freeform prose to construct a change. Extend the **Dope-owned response/presentation projection** narrowly with validated, bounded changed-entity before/after data, parent ID, action kinds, source-owned/link state and preview identity. Keep the authoritative full validated preview and approval token in the existing backend authority; never expose a reusable privileged token to the browser. Limit fields and counts; visibly disclose omissions. The UI may derive its mini-card/canvas appearances from this single projection without persisting a second Roadmap index.

Use existing schema-2 `gatePhaseCards`, `RoadmapCanvasWidget` and the provisional greenfield/strategic display pattern as presentation foundations, but **do not confuse** those revision-zero draft workflows with ordinary accepted-index `revision > 0` Gate proposals. A separate *transient overlay* for current accepted-index proposals is appropriate; it is not canonical project state, not another draft owner and does not issue source writes. Rendering a simple proposed row must reuse the visual grammar of real Gate cards. Rendering a complex request must stay exact and honest rather than fabricate an attractive miniature.

## Source authority, lifecycle and failure truth

- All actions remain one validated atomic review. Use the existing 1–3 action bound and actual Phase/Gate/Criterion/correction domain; no new model inference for rendering, no unreviewed mutation, no generated qualification evidence or Gate/Phase Green.
- **Unlinked schema-2 state:** preview `before/next` from existing `ProjectPlanningActions`; apply only through its checked revision/token path.
- **Linked Markdown:** source-owned changes use the current narrowly supported **single-field** reviewed Markdown patch with before/after hash and exact changed lines. Provisional canvas reflects only that field and labels `Linked Markdown · Not applied`; do not make structural/multi-action source-owned changes look approvable. Unsupported changes receive truthful review/synchronization guidance and no active preview.
- A pending preview is active only while its exact Chat/project/lease/source/revision proposal is valid. A saved historical Chat message **is not** authority to reapply. Reopen/restart may show an inert historical description, never revive an approval token. Lost owner, project switch, cancelled turn, new replacement proposal, stale revision/source, linked external edits, failure/rejection or disposed canvas invalidate/clear the overlay; do not leak preview between chats, tabs or projects.
- Preview navigation runs once per new valid proposal when the Roadmap tab is already active, or after an explicit **View in Roadmap** click otherwise; use existing selection/locate methods without stealing Chat keyboard focus during automatic preview, and preserve saved viewport preferences and manual pan/zoom. Avoid forced Fit All, surprise persistent camera writes, excessive motion or opening a second Roadmap instance. Respect reduced motion, keyboard focus, accessibility and narrow Chat docks.
- A final apply may update linked Markdown and source hashes; only actual authoritative outcome may be displayed as accepted. Reject/no-op/failed-before-write must leave canonical bytes and revision unchanged. For a partial or uncertain write, do not imply success/rollback without reading owner state; report recovery truthfully.
- Preserve Pi tool-driven source discovery, reasoning/provisional versus formal-final streaming, normal/diagnostic copy, permissions, saved-Chat continuity and strict project/source isolation. Preview UI work may not slow down Pi tokens/tool execution or hold file writes for animation.
- Do not resurrect persistent `Following active selection` or generic `Roadmap Chat editing unqualified` notices under every response.

# Roadmap phase orchestration — forward implementation contract

**Date:** 2026-11-03. **Authority:** [ADR 0049](../../decisions/0049-roadmap-phase-orchestration.md). **Stack:** [c12-rm-orch](../../tasks/c12-rm-orch/README.md). **Status:** DOCS ONLY, NOT IMPLEMENTED OR QUALIFIED.

## 1. Single entry and source-of-truth

Create one `generateRoadmap`-equivalent first-class controller entry (actual symbol chosen after local source inspection) used by greenfield Chat/Planning. It is a state machine, not a second model/provider/Chat session manager or a parallel Roadmap store. Reuse current Pi invocation, selected model and project context access; trusted Chat/backend owns generation session identity and authorization. Controller alone sequences phase units; the model cannot trigger additional unbounded controller steps.

Proposed states: `idle -> initializing -> generating-phase -> validating -> staging -> generating-phase ... -> review-ready`, with terminal `failed/cancelled/stale/incomplete` as appropriate. A failed or cancelled session has no apply lease. State/event transitions are monotonic, project-bound, generation-ID-bound and idempotent under duplicate/delayed provider events. On restart, do not silently resume without fresh project/source/model verification and owner authorization. An inspectable partial draft is NOT automatically valid for Apply.

## 2. Phase unit contract

Controller reads bounded project context and current accepted Roadmap once as an initial snapshot, then only relevant updates. It maintains compact explicit scope ledger, staged Phase summaries, stable IDs and outstanding requirements. Each model request covers exactly the **next Phase**, with bounded title/objective and small concrete Gates with observable Criteria. Tool use may consist of one bounded typed phase-create/stage operation or several serial per-Gate edits, depending on what the installed runtime demonstrably supports. Dope, not the model, supplies operation IDs, owner project, revision/source identities and parent relationships. One validated Phase completion is the scheduling barrier for the next Phase; no parallel phase calls within a session.

No model-facing full-plan JSON, RM1, deterministic Markdown grammar, natural-to-format conversion or fallback to old generator. Existing typed native operation schemas (not a whole-Roadmap output envelope) remain permitted and must be minimal and correctly discoverable. Non-text tool use should not force fabricated model reasoning. Captured reasoning streams remain visible when the selected provider supports them; progress is visible independently as genuine staged changes.

## 3. Validation, coverage and bounds

Before each stage transition, validate versioned typed operations, required text and lengths, nested parentage, duplicates, stale source/revision, scope, permissions and exact expected stage; never drop malformed Gates or infer missing Criteria. Include one bounded corrective attempt for a specific Phase when safe; on repeated failure mark session Incomplete/Failed rather than restart or switch format. Use controller-configured ceilings for number of phases, per-phase gates, per-phase subcalls, total calls/tokens, idle stall and wall-clock. Record actual limits/usage/finish reason where provided; missing telemetry is explicitly unknown.

Distinguish deterministic **structural validity** from **semantic project completeness**. The scope ledger records user requirements, explicit model claims of coverage, and unresolved/missing items; claimed coverage is untrusted and surfaced for review. No invented Gate qualification, fake confidence score or model-driven GREEN. Do not silently stop solely because a model says `done` or because five phases exist; stop when bounded scope goal is met or a truthful incomplete/limit terminal state is reached. A best-effort draft may be presented for human editing only after reviewed dependency/completeness preconditions are satisfied.

## 4. One proposal and asynchronous live canvas

Reuse the current noncanonical staged owner/projection and project-scoped revision/source/lease protection. Validated phase or gate stage events update a **single proposal ID**, with monotonic sequence and actual counts. The existing Roadmap canvas renders only validated Phase/Gate/Criterion ghosts; it may coalesce/drop intermediate render notifications, but backend stages and audit data cannot be dropped. No per-Phase proposal cards, fake typed/accepted status, independent UI store or async UI round-trip required for model progress. First eligible projection may locate itself once; subsequent updates do not pan/zoom or switch tabs. Respect active-tab-only auto-view, manual View action, historical browsing, keyboard and reduced-motion preferences.

During generation show true `Generating` and staged counts. `Ready for review` only after controller finalization and dependency-closed validation of the entire proposed set. Cancel/fail/source or model drift removes any approval authority; partial proposals may be inspected but cannot be applied without fresh owner-approved validation. A user may keep working in Chat or Roadmap without disrupting model/tool execution; permission prompts and cancellation remain responsive.

## 5. Apply, sync, safety

Owner Apply/Reject individually, Phase with descendants, selected, or all remaining through existing authoritative review. Explicit Apply atomically updates canonical schema-2 with exact project/source revision/lease checks. Linked Markdown is then synchronized through its separate verified source authority, with honest pending/conflict/failure. Rejections and failed validation do not produce an applied History receipt. Accepted qualifications/evidence/waivers/coverage never become writable via generation. Preserve protected /roadmap and greenfield permissions, Ask/Allow, source-root/symlink/overwrite safety, durable history/restore, fresh-source repairs and cross-project isolation. Prevent stale or cancelled completions from appearing as fresh proposals.

## 6. Clean retirement and verification

Delete executable legacy greenfield generation modules/entry routes/prompts/flags/parsers/converters/test fixtures exclusively supporting old methods; remove transitive dead imports, tests asserting retired behavior and duplicated generation UI state. Replace with meaningful regression tests for the new single entry. Do not erase historical reports/docs, general read-only Chat planning, other source-import parsers, ordinary code markdown rendering, or validated typed proposal owners used by manual edits.

P1 is a fail-closed cutover: old generation routes unavailable, not forwarded to a legacy fallback; P2–P3 progressively install new controller/phase capabilities. Before every run inspect **local** Git HEAD, worktree, dirty D2 edits and intended removals. Runner checkpoint commits never constitute independent qualification. P7 must observe a real selected-local-model tower-defense generation: at least five ordered MVP delivery Phases with Gates/observable Criteria covering waypoint path; spawn/health; cooldown tower, targeting and projectiles; waves; kill-earned money and spendable towers/abilities; persistent main-tower health; loss at zero. Prove intermediate canvas events, source/no-write before Apply, selective owner Apply, reload and Markdown. Record time to first staged Phase and final draft, total calls/retries, outcome/usage where known. Browser is not native Electron proof. If live model/host is unstable, preserve NOT GREEN/EVIDENCE GAP without repeated crash-risk trials.

# Roadmap phase orchestration — forward implementation contract

**Date:** 2026-11-03; **refinement:** 2026-11-04 (America/Chicago). **Authority:** [ADR 0049](../../decisions/0049-roadmap-phase-orchestration.md). **Stack:** [c12-rm-orch](../../tasks/c12-rm-orch/README.md). **Status:** CONTINUOUS TOOL-LOOP FORWARD DESIGN — DOCS ONLY, NOT IMPLEMENTED OR QUALIFIED. Historical P1–P6 implementation checkpoints and P7 NOT GREEN stand.

## 1. Single entry and source-of-truth

The **sole executable entry** to the Roadmap Generation Controller is a **trusted user-authored Chat submission** starting with the exact leading command `/gen-roadmap <roadmap prompt>`. Parse at the Chat command boundary **before any Pi inference**; after normalizing outer composer whitespace, require the exact `/gen-roadmap` token, a whitespace separator and a nonempty trimmed prompt (multiline body allowed). Strip the token before passing the body to the controller, retain trusted user-command provenance, and show usage with **zero controller/inference/stage/write calls** for missing body. Never scan quoted/code/prose content or model/tool output for executable commands. No intent classifier or natural-language routing, no automatic greenfield or Planning invocation, no `/roadmap` or `/roadmap generate` alias, no direct Generate Roadmap button, Work, injected tool/model text, old-format fallback or replay invocation. A retained UI affordance may only prefill the command for the user to submit. Normal Chat/Planning and ordinary `/roadmap` editing are unaffected. The command conveys requested intent, **not** permission to bypass Ask/Allow, project/source/revision/lease checks or final owner Apply.


Create one `generateRoadmap`-equivalent first-class controller entry (actual symbol chosen after local source inspection), reachable **only through the explicit user Chat `/gen-roadmap <roadmap prompt>` command**, never generic greenfield Chat/Planning. It is a state machine, not a second model/provider/Chat session manager or a parallel Roadmap store. Reuse current Pi invocation, selected model and project context access; trusted Chat/backend owns generation session identity and authorization. The controller admits/validates **each sequential native tool operation** and owns budgets/expected Phase/stage; the model may propose additional Phases in its **same protected Pi execution** but cannot force admission, bypass stage validation or trigger unbounded work.

Proposed states: `idle -> initializing -> generating-phase -> validating-tool -> staging -> generating-phase ... -> finalizing -> review-ready`, with terminal `failed/cancelled/stale/incomplete` as appropriate. Model and trusted tool-handler state are separate: a tool request is not success until validation **and** staging finish. A failed or cancelled session has no apply lease. State/event transitions are monotonic, project-bound, generation-ID-bound and idempotent under duplicate/delayed provider events. On restart, do not silently resume without fresh project/source/model verification and owner authorization. An inspectable partial draft is NOT automatically valid for Apply.

## 2. Phase unit contract

Controller reads bounded project context and current accepted Roadmap once as an initial snapshot, then only relevant updates. It maintains compact explicit scope ledger, staged Phase summaries, stable IDs and outstanding requirements. **One trusted user command starts one protected continuous Pi execution**, rather than a fresh inference context for each Phase. Within that execution, the model proposes the next Phase using `roadmap_phase` with bounded title/objective and small concrete Gates/observable Criteria. The Dope tool handler must validate the actual expected index and stage that Phase through the existing native owner **before returning a successful result to Pi**. Dope, not the model, supplies operation IDs, owner project, revision/source identities and parent relationships. A successfully staged Phase unlocks the next Phase tool request. No parallel stage calls, out-of-order phases, duplicate stage replay or competing proposal owners. Where the current model needs smaller Gate edits, the controller may admit small serial native operations under the same Phase, not a new full-plan format.

No model-facing full-plan JSON, RM1, deterministic Markdown grammar, natural-to-format conversion or fallback to old generator. Existing typed native operation schemas (not a whole-Roadmap output envelope) remain permitted and must be minimal and correctly discoverable. Non-text tool use should not force fabricated model reasoning. Captured reasoning streams remain visible when the selected provider supports them; progress is visible independently as genuine staged changes.

## 3. Validation, coverage and bounds

Before each stage transition, validate versioned typed operations, required text and lengths, nested parentage, duplicates, stale source/revision, scope, permissions and exact expected stage; never drop malformed Gates or infer missing Criteria. Allow at most one narrowly targeted retry/correction for an invalid Phase tool operation when safe; on repeated failure mark session Incomplete/Failed, stop the Pi loop and reject later results rather than restart or switch format. Failed validation/staging must return an honest structured tool error, not a successful acceptance receipt. Use controller-configured ceilings for number of phases, per-phase gates, per-phase subcalls, total calls/tokens, idle stall and wall-clock. Record actual limits/usage/finish reason where provided; missing telemetry is explicitly unknown.

Distinguish deterministic **structural validity** from **semantic project completeness**. The scope ledger records user requirements, explicit model claims of coverage, and unresolved/missing items; claimed coverage is untrusted and surfaced for review. No invented Gate qualification, fake confidence score or model-driven GREEN. Do not silently stop solely because a model says `done` or because five phases exist; `roadmap_finish` is a proposal to finish, not authority to mark complete. Check actual server-staged Phase/Gate/Criteria projection, requirements ledger, dependency closure, source basis and current owner lease before `review-ready`. Stop when bounded scope goal is met or a truthful incomplete/limit terminal state is reached. A best-effort draft may be presented for human editing only after reviewed dependency/completeness preconditions are satisfied.

## 4. One proposal and asynchronous live canvas

Reuse the current noncanonical staged owner/projection and project-scoped revision/source/lease protection. Validated phase or gate stage events update a **single proposal ID**, with monotonic sequence and actual counts. The existing Roadmap canvas renders only validated Phase/Gate/Criterion ghosts; it may coalesce/drop intermediate render notifications, but backend stages and audit data cannot be dropped. No per-Phase proposal cards, fake typed/accepted status, independent UI store or async UI round-trip required for model progress. First eligible projection may locate itself once; subsequent updates do not pan/zoom or switch tabs. Respect active-tab-only auto-view, manual View action, historical browsing, keyboard and reduced-motion preferences.

During generation show true `Generating` and actual staged counts. After each successful `roadmap_phase` tool-stage, immediately show its validated card with nested Gates/Criteria as `Staged · Provisional`, while the controller permits subsequent tool calls in the same Pi execution. Show a lightweight **`Generating next Phase…` placeholder** at the next Phase position with a subtle pulse/spinner; never render guessed title/Gates, fake Phase identity/count or acceptance. Replace the placeholder only with actual validated staging, or remove it on finish, cancellation, timeout, incomplete, failure or stale. Animations are UI-only, asynchronous and nonblocking; honor reduced-motion with static text/icon, motion-safe focus, active-tab-only preview, user camera and historical-mode isolation. `Ready for review` only after controller finalization and dependency-closed validation of the entire proposed set. Cancel/fail/source or model drift removes any approval authority; partial proposals may be inspected but cannot be applied without fresh owner-approved validation. A user may keep working in Chat or Roadmap without disrupting model/tool execution; permission prompts and cancellation remain responsive.

## 5. Apply, sync, safety

**Distinguish two meanings of accepted:** a tool-accepted Phase is noncanonical `Staged · Provisional`, while an **owner-accepted** Phase exists only after authorized Apply and is shown with real canonical Roadmap visuals. Never make staged Phases appear completed/GREEN or enable Apply prematurely during an incomplete generation. Owner Apply/Reject individually, Phase with descendants, selected, or all remaining through existing authoritative review. Explicit Apply atomically updates canonical schema-2 with exact project/source revision/lease checks. Linked Markdown is then synchronized through its separate verified source authority, with honest pending/conflict/failure. Rejections and failed validation do not produce an applied History receipt. Accepted qualifications/evidence/waivers/coverage never become writable via generation. Preserve protected /roadmap editing and explicit /gen-roadmap generation permissions, Ask/Allow, source-root/symlink/overwrite safety, durable history/restore, fresh-source repairs and cross-project isolation. Prevent stale or cancelled completions from appearing as fresh proposals.

## 7. Prospective continuous Pi tool-loop correction (2026-11-04)

**Supersession:** Sections above describe the current forward behavior. The original single-model-call-per-Phase scheme and its P1–P7 prompts are historical source/evidence, **not** a second mode or fallback. See [tool-loop recovery plan](../../tasks/c12-rm-orch/continuous-tool-loop/README.md). Do not rewrite historical prompts or P7 NOT GREEN. This amendment does not authorize an immediate code change or imply qualification.

**R1 — Protected serial tool loop.** Use an actual Pi worker session to execute `roadmap_phase(1)`, return only the validated/staged receipt, then accept `roadmap_phase(2)` in the same execution, finally `roadmap_finish`. A second Phase may not be rejected merely because one successful tool operation already occurred. It may be rejected if duplicate/out-of-order/stale/invalid/unauthorized. The single noncanonical proposal identity and stage sequence must remain stable across tool calls. Model tool calls can be emitted rapidly or in groups; mutations are serialized and revalidated against current authority immediately before each stage. No stage is acknowledged until committed to the noncanonical owner.

**R2 — Canvas and safety.** Stage projection updates and one next-Phase loading affordance after each successful tool result. Verify the loader has no fake card identity/count/Gates, moves forward only after validated stage, never blocks inference, doesn't move camera/focus, and becomes static under reduced motion. On owner Apply, staged entities become canonical accepted entities with linked Markdown/History checks. On terminal failure/cancel, noncanonical approval authority is invalidated and loader removed. Tests include token/tool budget, tool loop stop, stale source or lease between phases, duplicate/parallel calls, old-format pathways absent, project/tab switch, provider progress, UI dismount and late tool callbacks.

**R3 — Exact-source local-model qualification.** One authorized Qwen3.5-9B run with exactly two Phases (fixed waypoint rendering then one enemy following the path, one Gate/two observable Criteria each), followed only on success by full tower-defense MVP qualification. Capture true stage receipts/canvas snapshots, first and second Phase arrival times, full session wall-clock, tool counts, no-write before owner Apply, owner Apply/Reject/persistence. Record runtime/quality regressions and independent native Electron evidence separately. A model thought or a `tool completed` transcript without server staging proof is insufficient.

## 1. Protected baseline and authority

The November 4 two-Phase Qwen3.5-9B source-bound run demonstrated serial `roadmap_phase`, `roadmap_phase`, `roadmap_finish` inside one Pi execution, validated noncanonical staging, in-canvas live provisional progress and selective owner Apply/Reject; it ended PARTIAL / NOT GREEN on unresolved source and browser cases. Freeze that architecture during this polish effort. Preserve one RoadmapStore/Service/ProjectPlanningActions authority, real StageOwner receipts, no canonical/Markdown/History write before explicit Apply, checked exact-root/revision/source/lease, user-origin `/gen-roadmap`, Ask/Allow, Gate-set coverage/evidence and separate GREEN, and linked Markdown's source-protected automatic sync. No return to full-plan text/JSON/RM1/two-pass generation or per-Phase inference fallback.

## 2. Element control tab component

For **every pending selectable** Phase, Gate, Criterion and Correction/change, render one consistent and discoverable tab protruding from the element's **upper-right border**. The tab is part of the element card, not a free-floating unrelated menu. The control order is **checkbox / check / X**:
- Checkbox toggles selection without applying or rejecting; reflect current selection, mixed/partial selection where relevant, and descendants explicitly. If the underlying proposal has only a parent operation owning nested Criteria, map a Criterion interaction to an exact backend-approved owning operation instead of inventing a new operation ID. Do not show a misleading individually applicable control if independent decision is impossible; explain dependent scope in tooltip/confirmation.
- Check opens the existing **Apply preview** for that element or dependency-closed group; final canonical write happens only after separate deliberate Confirm using current owner lease/source/revision validation. X opens the existing **Reject preview** or its current reviewed rejection path; never silently cascade across unrelated operations.
- Buttons have **icons only** on their surfaces, semantic aria-label/title, keyboard Tab/Space/Enter, visible focus rings, adequate hit areas and disabled/busy/terminal states. Tooltip/confirmation gives precise Phase+descendant semantics. Avoid hover-only visibility and button overlap with the pencil editor, expansion chevron, Phase title, scrollbars or React Flow handles. Ensure tabs are not cut off by node/viewport clipping and remain useful at reduced zoom/narrow viewport.
- Styles derive from Dope theme tokens when Dope dark theme is active; semantic success/danger must remain restrained and accessible. In every other theme use the existing general Theia/editor variables, not Dope-specific colored overrides. Responsive behavior must not move the tab inside content or create new panel clutter.
- Bulk selection and Apply/Reject Selected/All Remaining remain available in a **compact icon-oriented integrated canvas toolbar** with counts and accessible labels; do not remove group/remaining operations or duplicate the large text-button bar. Explicitly test parent/descendant closure, mixed selection, stable IDs, stale lease, partial Apply/rebase and reject of Phase without orphaned Gate.

## 3. Chat message structure, no redundant tool list

For each assistant message the visual sequence is: **reasoning/real activity including native tool events** → **final answer** → **one inline authoritative proposal/result card** → **footer (copy, info, time) as last normal in-flow child**. Remove the duplicate `Tool calls (N)` `details`/list and CSS branch; do not drop `execution.toolEvents`, timeline events, stable IDs, truthful broker/argument/authority statuses, History provenance or copy-with-reasoning. If reasoning content is empty, preserve actual tool activity (not fake thought) in the normal timeline. Correct saved/live/reloaded/failed/cancelled views without duplicate rows or missing tool evidence. Preserve paragraph-batched reasoning animations and follow-bottom scrolling.

Response info must open above the footer in a controlled integrated detail region or anchored popover, never an extra block beneath footer. All Roadmap completion/confirmation/result banners must be rendered inside final content or its single compact status card before footer; no delayed append beneath actions. Update existing saved card after Apply/Reject, don't create a second confirmation paragraph. Make final reply truthful: completed staged generation is not "applied"; a selective Apply describes actual accepted/rejected counts. Remove giant repeated yellow warnings from default visible card; retain sanitized, bounded full diagnostics/unresolved user goals and scope questions under one disclosure. Keep raw JSON/debug data only in optional diagnostics, not default UI.

## 4. History projection truth and cleanup

Project History currently reads durable Roadmap revision records for restore entries but may omit normal approved Apply. Project actual-effect event should derive deterministically from verified durable receipt/revision with accepted operation identities/affected counts, real timestamp and stable source ID. Include Apply (and any distinct approved transaction type supported by source evidence), preserve restore and write provenance, and avoid duplicate events for source sync, reload or repeated reads. No entries for staged/failed/denied/no-op transactions; do not change canonical approval writer, source hashes, evidence, waiver or restoration semantics.

P1 establishes source-drift negative (specifically a source change between serial Pi worker Phase calls) and owns disposable-fixture cleanup failure attribution. Distinguish test setup/teardown failures from real product defects, fix only observed causes, prove no unsafe stage/Apply following a source change and ensure fixture ownership cleanup is bounded and race-safe. P3 removes unreachable/obsolete nonvisual generation status/helpers/duplicate diagnostics only after proving imports/callers unneeded; it must NOT preempt M1/M2's UI component cleanup or remove archived Chat history readers.

# Roadmap revision navigation and reviewed restoration — owner-approved contract

**Date:** 2026-11-01 (America/Chicago). **State:** DESIGN APPROVED; DOCS / PROMPT AUTHORING ONLY, NOT RUN / IMPLEMENTED / QUALIFIED. **Baseline:** `0.12.7` unchanged. [ADR 0046](../../decisions/0046-roadmap-revision-navigation-and-restore.md) · [c12-undo](../../tasks/c12-undo/README.md).

## Existing authority and observed limitations

Dope's schema-2 canonical Roadmap is `Phase -> Gate -> Criterion` (plus Corrections), owned by `packages/project-intelligence/src/node/roadmap-store.ts`. It persists current `.dope/roadmap.json` with a monotonically increasing revision and guarded root/identity, but its revision counter is **not** itself a durable historical archive. `packages/project-intelligence/src/node/project-planning-actions.ts` maintains one handle-local `before/after` undo record cleared on detach, and `roadmap-inspector-model.ts` / `roadmap-inspector-widget.ts` expose an eligible one-step undo. This cannot power restart-safe multi-step browsing. `roadmap-canvas-widget.ts` owns the existing center-editor toolbar, canvas, camera/selection and provisional Chat preview. `RoadmapStore.saveGateIndex` rejects unauthorized qualification, evidence, coverage and linked-source changes. Verify actual *local* code prior to implementing: GitHub-main source is an assessment, not a local-state guarantee.

## 1. Toolbar and interaction semantics

- Always-visible **Undo** (back) and **Redo** (forward) icon controls sit together in the Roadmap center-editor toolbar. Use existing Codicon/Dope theme, accessible names/tooltips, focus indicator and disabled affordance. No separate panel or second Roadmap widget. Do not commandeer system code-editor keyboard undo/redo.
- These controls change only a **view cursor** among *available exact retained revisions*, never the current authoritative index or linked source. Undo from current selects the nearest previous available revision; Redo walks forward toward current. Disable on oldest available and current respectively. No fake 'undo available' if history has not yet been captured.
- Historical snapshot mode renders real stored Phase/Gate/Criterion/Correction records, parent/order/dependencies, and their *as-of-then* display state labelled **Historical preview · Rn / current Rm**. As-of-then statuses are contextual historical facts, NOT current qualification assertions. The live current Roadmap remains unchanged.
- While historical: suppress current editing/Inspector Edit, approve/reject controls that would act on current source, context-picking or active transient proposal overlay; do not leave source writer buttons erroneously active through the historical display. Keep ordinary pan/zoom/expansion behavior without rewriting saved current viewport/camera preferences. Provide keyboard-accessible **Return to Current / Cancel**.
- A compact, non-obscuring **bottom confirmation strip**, distinct from removed redundant canvas revision narration, appears only while view cursor != current: revision, noncanonical warning, **Compare with Current**, **Confirm Restore Rn**, **Return to Current**. Confirmation means reviewed action, not immediate silent write. The strip disappears at current.
- On new authoritative head arriving during historical preview, do not silently jump to current or switch history cursor; show current-head changed and require fresh comparison/approval. Invalidate a pending restore review if its expected head/source changes.
- The user can change editor tabs or reopen the Roadmap without losing canonical data. It is acceptable to return to **current** on reopened editor/restart; do not replay a stale restore confirmation or invent persistence of ephemeral view cursor.

## 2. Durable revision capture and read

- Record a **verified baseline** at feature activation from the current schema-2 index, with project/root/owner, schema, index revision, exact content digest, optional linked source path/hash and capture provenance. Do not label earlier unrecorded revisions browseable.
- On **every applicable successful authoritative committed revision**—manual, Chat-approved Gate edit, import/replace, greenfield acceptance, linked sync/relink/publish, source-backed qualification/evidence, and later restore—retain an immutable exact snapshot or lossless, reconstructable equivalent with ordered revision ID, original bytes/hash, parent/predecessor identity, committed outcome and source metadata where available. Capture belongs in the single Roadmap owner boundary and does not depend on UI visibility or provider.
- Use project-local versioned metadata under `.dope/` (or owner-selected equivalent established against local source) with safe canonical paths, symlink checks, locking, bounded retention/quota and integrity verification. Define whether an archived revision and live write are committed together or reconciled by a durable journal. Ensure crash/restart cannot falsely expose a revision as saved or drop a committed revision silently. No separate writable Roadmap authority. Detect missing/corrupt/gapped history explicitly; protect current `.dope/roadmap.json`.
- Provide bounded index/list and per-revision read RPCs through the existing `RoadmapService`, with project/owner checks, hashes, schemas, size and optional pagination. History reads must not mutate Roadmap/Markdown or run models. Distinguish historical display from current owner snapshots and do not leak archived state across projects.
- Recording future revisions does not mean retrospectively reconstructing unknown prior revisions. If an exact current baseline at R8 is first retained, the UI cannot navigate R1–R7 unless independent exact proof and a separately approved migration genuinely exists. A contiguous range may be limited by safe retention; reveal bounds and gaps honestly.

## 3. Reviewed restore operation and append-only semantics

- **Compare with Current** resolves a verified immutable target snapshot and latest owner state. Show structural before/after summary and exact affected Phase/Gate/Criterion/Correction adds/removals/moves/fields, plus current vs historical qualification/evidence implications, linked-source changes, stale external references and unsupported operations. No mutation in preview.
- The restore review binds project/root/owner, verified historical revision/digest, expected *current head* revision/index digest, source path/hash/fingerprint, precise proposed structural resulting index, claimed changed IDs and a short-lived approval identity. Revalidate under the owner lock when developer explicitly confirms. Duplicate clicks/retries are idempotent by one stable restore application identity. Reject/stale/no-op and failed zero-effect outcomes must write neither current Roadmap nor source nor applied History entry.
- Successful restoration creates exactly **one new monotonic head revision**: e.g. R9 -> chosen R5 -> new R10 whose editable structure matches R5, retaining R6–R9 and original R9 as navigable history. The new revision records `restoredFromRevision=5` and `previousHeadRevision=9` plus real outcome/time. It does not rewrite R5 or pretend that R9 disappeared.
- The **restorable target** is editable plan structure: Phase/Gate/Criterion/Correction identity, objectives, title, relationships, dependencies and order, subject to current validity. It is NOT blind replacement of current protected qualification/evidence/waiver, Gate-set approval, Work/Chat/history, deployment/source linkage or owner identity. Retain immutable historical evidence records, preserve current audit provenance, and compute current qualification freshness: affected Gate-set coverage must be revoked/reviewed, affected Gate/Phase qualification becomes stale/unknown pending fresh evidence as required, never silently Green. If protected-data reconciliation cannot be verified, block with exact explanation.
- For an **unlinked** Roadmap, apply only via a dedicated typed, validated schema-2 Roadmap owner operation respecting IDs, dependencies, atomicity, history capture and qualification rules. Do not bypass normal `saveGateIndex` checks with raw snapshots or generic file overwrites.
- For a **linked canonical Markdown Roadmap**, restore requires an inspectable source-aware diff preserving unrelated prose, stable section mappings and supported grammar, current hash/path/owner checks, explicit approval and existing single canonical Markdown/source authority. Structural multi-field restoration is broader than the currently supported linked single-field Chat patch. Implement an explicit reviewed owner operation with safe crash recovery, or **block unsupported linked restores without changes**. Never overwrite `ROADMAP.md` from arbitrary historical bytes, replace external edits, silently unlink, or bypass `c12-roadmap-publish-ux` Unit B publication state.
- A crash between document and index writes requires a durable exact intent, recovery verification and truthful partial/uncertain state; do not claim rollback or success from absent evidence. Preserve the current file on collision/hash drift. The confirmed restored revision becomes a truthful source-linked state only after canonical source verification.
- Current pending Chat proposals remain in Chat but are invalidated/revalidated by backend owner/revision/source rules after a confirmed restore. Do not revive old approval tokens. Work/agent executions, Git commits and evidence are not rerun/reversed. No AI inference, Work grant or independent publisher is implied.

## 4. Interactions with Chat, History and tabs

- If a new validated Chat Roadmap proposal arrives while the Roadmap editor is **active but displaying a historical revision**, the conditional auto-preview rule is suppressed. Do not replace the user's historical selection, clear their comparison or steal Chat focus. The **View in Roadmap** button remains available on valid pending cards; explicitly return to current before showing the proposal or ask the user to do so. No implicit application.
- If another center editor is active, existing Chat preview never takes focus; if the Roadmap is closed, it remains closed. Existing conditional auto-preview rules otherwise stand unchanged.
- The right-toolbar Project History remains a **read-only projection**, deriving one entry from each verified successful restore owner receipt, with selected revision/new revision, actual changed objects and true actor/time when known; no entry for review/reject/no-op/failed-zero-effect. History never owns snapshots, writes or recovery.
- Preserve single ChatPanel, proposal-card lifecycle, clean/diagnostic copy, source-bytes safeguards, model/permission boundaries, non-Green statuses and no extra model calls.

## 5. Qualification and failure policy

1. History capture: baseline Rn, multi-edit/multi-owner successive revisions, exact hash and identifiers, restart/reopen persistence; early unavailable revisions and gap/corrupt/history quota truth. Include outside-Chat edits.
2. UI: back/forward through multiple retained revisions, accurate Phase/Gate/Criterion order and status for every snapshot, toolbar disabled states, read-only Inspector, safe pan/zoom, bottom confirmation and Return to Current without changing index or linked source bytes.
3. Unlinked restore: compare selected Rk against current Rm, reject/no-op, confirm => Rm+1, browse old Rm and target Rk, repeated click/restart dedup, no lost revisions.
4. Qualification/evidence: old Green/waiver must not become current Green; actual source/evidence preserved; affected qualification stale with explicit explanation; illegal IDs/dependencies/ownership rejected.
5. Linked Markdown: source-exact preview, safe approved restore with stable mapping and unrelated prose preserved where supported, and explicit no-write for unsupported operation, external edit/hash change, symlink/root escape, stale review, collision, crash/retry/recovery.
6. Race and project isolation: new revision during preview, concurrent windows/Chat pending proposal, project switch, late callbacks, reopening and history restore all fail closed; no focus hijack.
7. Real **connected Codex Chrome**: narrow/wide Roadmap editor, Undo/Redo icons and status, selected historical canvas/confirmation, actual unlinked review/reject/confirm, linked negative/positive as supported, Chat auto-preview suppression in historical mode, no duplicate History and no corrupt source on restart.
8. Focused unit/integration source tests, typecheck, browser and Electron builds with exact final source; show actual test counts, fixture bytes and screenshots. Native Electron GUI remains owner-operated/unproven unless separately exercised. Any mandatory unobserved case is **NOT GREEN / Evidence Gap**.

## Goal and ownership

The developer describes a feature or change in the **existing ChatPanel**, then types `/skill-name`. Dope adds that skill's bounded instruction block to the **current turn** of the selected model, together with the saved conversation. A skill is instructions—not a new agent, shell tool, permission, file writer, background task or model. Reuse current Chat, Pi, context composition, AI Center, brokered tools, Roadmap, Work and History owners.

Pi natively supports Agent Skills directories with `SKILL.md`, name/description discovery, on-demand loading and `/skill:name` invocation ([upstream reference](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md)). Inspect the **actual pinned bundled Pi version** and its Dope host APIs before choosing an adapter. Prefer its supported representation/loader while making Dope's friendly `/name` alias deterministic; never rely on a naked model-visible command or double-inject the body through Pi and Dope. Do not modify global Pi configuration or silently trust external skills.

## Targeted implementation prompt 1 — Skills foundation

1. **Slash menu:** When the user types `/` in a command position, show a compact menu anchored to the existing fixed-height Chat composer; case-insensitive prefix matches first, then simple character/substring matches. Show name, short description and built-in/custom provenance. Arrow keys, Enter/Tab, Escape, mouse/touch work without breaking IME, editable drafts, Enter-to-send, attachments, narrow panes, selection/copy or scrolling. Selecting inserts an editable command, never automatically submits. Don't intercept literal slashes in code or file paths. Filtering invokes **zero models**.
2. **Registry and persistence:** A skill has stable ID, canonical command, description, limited plain-text instructions, built-in/custom provenance and enabled status. Ship protected built-in registration capability; let users add/edit/delete/disable their custom skills in a simple manager. Persist custom skills in Dope-owned user settings across restart and project switching. Reserved names and collisions fail visibly; custom skills never override protected built-ins. A safe sample built-in or fixture may test foundation; **do not register functional Docs skills in this first prompt**.
3. **Bounds:** Prefer portable Agent Skills names (1–64 lowercase letters/digits/hyphens; no leading/trailing/doubled hyphens). Require description/body and validate before saving or using. A **suggested 1,500-character custom instruction ceiling** and actual local-context budget guard keep text small; measure fit with the selected model. No arbitrary scripts/assets/packages in this MVP.
4. **Deterministic invocation:** Resolve exact invoked skill at send time and include its instructions once for that turn, with trailing arguments and previous conversation. Preserve a bounded turn-scoped skill snapshot/version/digest for retries and saved Chat; editing a skill later cannot silently alter a retry. Do not include uninvoked **skill bodies** in normal turns; a minimal catalog of names/descriptions is acceptable when bounded. Missing, disabled or renamed skill must fail understandably rather than silently falling back. Do not add a selector/summarizer model call.
5. **Safety and compatibility:** Skill text is untrusted instructions and cannot expand Pi tool authority, Ask/Allow, sandbox, paths, network, canonical writes, Docs publication, Work grants, Roadmap approval or Git mutation. Keep the same model/provider/local-only behavior; scope or explicitly report unsupported non-Pi modes rather than swapping models. No second agent/Chat/permission engine.

**1 qualification:** In a disposable Chrome project, create and save a custom skill, filter and select it by slash, invoke it following a normal feature discussion, confirm the already selected Pi model follows the exact bounded skill text and retains prior context. Test unskilled control (no body leak), reload, edit-and-retry stability, collisions, disabled/malformed entries, keyboard/narrow view and existing Chat context/copy/attachments, Ask/Allow, Roadmap and Work. Run focused tests/typecheck/affected builds against exact final source. Native Electron evidence stays distinct. No Docs publication is required or implied.

## Targeted implementation prompt 2 — default Docs skills and progressive retrieval

Register two protected built-ins using the **qualified** generic framework. Preserve [ADR 0041](../../decisions/0041-planning-documentation-workflow-and-applied-history.md) and [the Docs application contract](documentation-workflow-contract.md) as governing authority.

**`/docs-review` — read-only.** Determine the review objective from preceding Chat feature discussion without requiring it repeated. Inventory **all eligible `.md` and `.txt` project documentation** within verified workspace/file boundaries. Use low-cost local listing, text/heading/path search and related keywords to discover candidates across the eligible corpus; distinguish authoritative current requirements from drafts, historical tasks and validation evidence. Have Pi read relevant bounded line ranges with surrounding context, expand to related headings/documents beyond first keyword hits, then report precise path/line corrections, contradictions, missing information, uncertainties and coverage. **Files enumerated or searched are not necessarily files whose contents Pi inspected.** Report skipped/inaccessible/truncated files rather than claiming comprehensive semantic inspection. No writes, proposals silently accepted, Work, or applied History from a review alone.

**`/docs-apply` — protected application only.** Resolve a **specific unchanged pending reviewed proposal**, not a newly inferred patch from the conversational command. Skill text never writes canonical files. The Dope-owned proposal/application service must enforce exact project/worktree/root/target/source/owner revision and approved diff, explicit developer application, eligible `.md`/`.txt` create/update only, safe paths and symlink protections, journaled crash/retry recovery, post-write byte/hash verification, correct zero/no-op/reject/partial effects and **exactly one applied-only History entry** carrying the original durable diff where changes actually remain. Linked Roadmap Markdown stays with the existing authoritative Roadmap writer. Commands Ask/Allow and ordinary Pi read/shell calls cannot authorize publication.

**Local inference cost:** The *explicit review* can scan all eligible filenames/text cheaply; Pi should receive only relevant sections and expand progressively. No embedding index, vector database, auxiliary model, mandatory full-document prefill or semantic summary service initially. **No automatic corpus scanning/prefill before ordinary Chat/Planning/Work turns**; optional relevant documentation references for Work stay deferred. Measure true search and local-model tool/read/response costs with matched control tasks. Check late-section reads and reported truncation.

**2 entry/stop gate:** Inspect actual local source first for a persistent reviewed proposal, inspectable exact diff, Dope-owned approval-bound application, journal/recovery, applied-only History and brokered Pi reads. The former unexecuted P3 explicitly warned some may be missing. If a safe publication service does not exist and cannot be delivered narrowly, **STOP — BLOCKED / SPLIT REQUIRED** with source-grounded dependency-ordered follow-ups. Neither `/docs-apply` skill text nor an agent's claims are evidence of successful publication. Preserve historical 15-prompt requirements without automatically running that stack.

**2 qualification:** In disposable fixtures, discuss feature → `/docs-review` → inspect source-grounded relevant `.md`/`.txt` diffs and prove no writes → explicit approval → `/docs-apply` → verify exactly approved bytes and one truthful applied-only History entry. Include rejected/no-proposal/no-op/stale/cross-project/protected/symlink, partial/retry recovery and linked Roadmap controls. Distinguish search coverage from actual Pi reads and inspect missing late sections. No Green absent real write/recovery/History evidence.

## Targeted implementation prompt 3 — protected `/roadmap` skill (C12 P3-C)

**Owner-approved forward amendment, 2026-10-31 America/Chicago; documentation only.** [P3-C](../../tasks/c12-planning-recovery/P3-C-roadmap-skill.txt) follows an independently qualified P3-A registry. It is a separate specialization alongside P3-B Docs, not a replacement for P2 Roadmap functionality or an assertion that P2, P3-A, P3-B, H1–H3, C12, or native Electron is Green. GitHub `main` records dated P2-R3 and H2 **NOT GREEN**; local implementation work must recheck the actual checkout and unresolved evidence before changing source.

**Behavior:** The protected built-in `/roadmap` is a *turn-scoped, explicitly invoked* entry to model-generated **schema-2 canonical Roadmap edit proposals**, not a standalone agent, model, writer, or security capability. Dope resolves the skill deterministically at Send, retains the bound identity/instructions snapshot for retry, and authorizes the edit-proposal route only when current-turn invocation is verified by Dope-owned request metadata—not model-visible command text or selected Roadmap context. No automatic skill activation in this delivery. The user may first discuss a change naturally and then enter `/roadmap` without restating the conversation. A missing/disabled/renamed invocation fails safely with visible explanation. Retry can reuse the exact skill snapshot but **must freshly validate** the current Roadmap root, revision, linked source, lease, and approval authority.

**Scope:** Preserve the existing ChatPanel, Pi broker, selected model, `ChatContextComposer`, `ChatBackend.gateProposal`, `ProjectPlanningActions`, `RoadmapStore`, schema-2 19 typed operations, 1–3 atomic-action envelope, validated preview and explicit human Accept/Reject. A selected Phase/Gate is optional: the backend may acquire the live Roadmap index and bind exact project/target identity, resolving unambiguous IDs/designations; ambiguous or absent targets get a useful no-action or clarification, never invented IDs. A skill invocation may yield a read-only answer, focus request or no-action without forcing a write. **Unskilled AI Roadmap mutation proposals are denied at the backend; ordinary discussion/read-only answers and selected Roadmap facts remain usable.** This restriction does not intercept human Inspector edits, imports, linked-source refresh/relink/reconciliation, greenfield draft creation, other explicitly authorized owner UI paths, or Work execution. Do not give skill text, Ask/Allow, ordinary file tools or user-controlled prompts direct write privileges.

**Progressive Roadmap context policy:** No full Roadmap schema, criteria/evidence bodies, or edit instruction prefill in unrelated Chat turns. When project-planning context is actually relevant, a small deterministic, read-only summary may include project identity, owner/source revision, active phase/gate and status counts if verifiable. Explicit selection or read requests load relevant Phase/Gate facts without the mutation grammar; `/roadmap` loads its **single** compact skill instruction body plus exact target/parent/dependency/field/source metadata required for the proposed action. A Gate-originated Work operation may use selected, approved requirements only through its existing Work authority; do not expand unrelated Work/context systems here. Expand bounded retrieval for additional targets/criteria only on demand; label omissions truthfully, and **fail closed rather than truncate** any identity, linked-source constraints or unchanged fields required for an atomic edit. Confirm source freshness immediately before preview/apply. Use no auxiliary model, embeddings, background scan, blanket context injection, or double Pi/Dope skill injection.

**Qualification:** Independently compare same-model, same-window normal/selected/`/roadmap` requests by actual serialized input tokens, tool calls, first response and total elapsed time when observable. Include a sufficiently large schema-2 fixture and a 16,384-context profile, no-context-overflow/mandatory-data-omission assertions, unselected and ambiguous-target requests, 19-action compatibility sampling, plain selected non-edit control, explicit mutation/preview/Reject/Accept, linked source-owned single-field approvals vs structural refusal, stale/conflict/cross-project/cancel/retry/lease denial, skill-body isolation, permission isolation, History exactness and existing hybrid preview reuse. Use the real connected Chrome UI and selected local Pi model on disposable fixtures, plus focused tests/typecheck/browser/Electron builds; native installed Electron remains independent. No production product work or qualification is performed by this documentation amendment.

# Qualification evidence retention

Use this review after a gate or phase reaches an explicit disposition. Qualification results remain in their existing closeouts; this procedure adds no parallel evidence authority. The [2026-11-02 balanced cleanup](2026-11-02-closeout.md) and [machine-readable manifest](2026-11-02-cleanup-manifest.json) show the record format.

1. Identify the authoritative closeout, exact tested source/tree, package hash and configuration. Keep earlier NOT GREEN and evidence-gap records with their original source and meaning.
2. List unresolved defects, regression baselines, supporting traces and retention exceptions. Active qualification and failure investigation keep the evidence needed to finish or reproduce the result. Recently completed gates keep final reports and significant diagnostics. For older closed gates, consolidate repeated raw logs into a sourced report with hashes, timestamps, counts, representative redacted diagnostics and retained exceptions before proposing deletion.
3. Inventory storage with exact paths and allocated bytes (`du -B1` or file `stat` blocks), then calculate SHA-256 for each proposed regular-file removal and every retained duplicate. Search documentation and scripts for references. Check for live writers/readers with process inspection and `lsof`, and verify no symlink or filesystem boundary will be traversed.
4. Record each candidate in a dated JSON manifest: exact path, phase/gate, classification, initial logical and allocated size, SHA-256 where applicable, retained equivalent, reason, verification and final disposition. Recommend candidates first. Remove only exact approved paths after a fresh identity check; skip changed, open or uncertain items. Verify the retained evidence and actual reclaimed allocated bytes after each stage.
5. Add a concise evidence index to the relevant phase closeout or active-phase index: disposition, verified source, tested package/configuration, authoritative reports, unresolved defects, retained hashes/artifacts, superseded evidence, exceptions and next review trigger. A historical path in a test report means the file existed then; if retired, the forward index and manifest identify its current availability.

**Retention boundaries:** Never automatically remove Git projects, `.dope` project state, runner records, installed releases, accepted changes or active qualification evidence. Reproducible cache deletion requires an explicit disposable classification and independent inactivity check. Protected or uncertain evidence requires owner approval before removal. Do not add cleanup to Pi, Chat, Planning or Work execution, and do not run background deletion, a watcher or a new database.

For future gates, a small inventory-only report may be generated from `find`/`du`/`sha256sum` and reviewed with the owner. Automated recommendations beyond this documentation, installed-release pruning, historical fixture consolidation and runner-record compaction require separate scope.

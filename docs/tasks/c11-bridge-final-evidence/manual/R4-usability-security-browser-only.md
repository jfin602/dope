## Priority: 75% usability / 25% security

Primary goal: after a four-hour development session, users should clearly understand **what the Work did, what changed, what passed or failed, what still needs their decision, and where to continue**. Make the existing Work module, candidate review, prompt-stack progression and transcript readable and human-centered. Preserve the restrained dark-orange identity: neutral secondary controls, orange for meaningful primary actions, compact machinery, focus accessible but subdued.

### Cycle 1 — Work supervision UX and decision clarity

In the **real browser**, enter Work from the existing selector. Exercise a completed run, a held/pending candidate, a blocked Work/stack run and an authored prompt sequence when source evidence exists. Reproduce actual confusing states before edits.

**Inspect and improve only the existing Work presentation**:
- Stable task title and clearly separated `Running`, `History`, `Prompt Stacks` navigation; no duplicate tabs or alternate Work UI.
- A compact, readable `P1 of N` authored-step progress rail, with **implementation**, **validation**, **candidate review**, **Git checkpoint** and **qualification** separately labeled; never infer complete/Green from an agent's words.
- Plain-language current state, cause of block, validation outcome, changed-file count and meaningful next action. `worktree-drift` and missing `tsc`/`ENOTCACHED` are separate problems with separate grounded guidance.
- Obvious but safe review/accept/reject/resume controls only when authorized and actionable; disabled actions explain why. Secondary controls recede, details (grant, fingerprint, raw diff/log) remain progressively disclosed and inspectable.
- Preserve Work/Chat dock flexibility, selected run and editor focus; no hidden Run or candidate acceptance from navigation.

Repair at most one coherent presentation/source-truth seam per iteration. Use existing Work selection/controller/widget and current task/run/sequence backend—not a parallel store, run controller or approval path. Tests should cover truthful controls, disabled states, order, project identity, and status transitions. **Browser PASS** requires a developer to tell the current state and safe next action without reading raw JSON.

### Cycle 2 — Formatted Work transcript and continuity

Use actual saved AgentRun transcript with Markdown headings, paragraphs, lists, task lists, code fences, inline code, tables, links and a real tool/command trace.

- Reuse the **existing Chat safe-Markdown presentation seam** for sanitized Work prose, not a new Chat system or transcript database. Comfortable centered reading column and readable spacing. Raw source remains the durable saved transcript.
- Machine-only tools/commands are muted compact expandable rows with useful labels; full command, error and diagnostic bytes remain accessible on deliberate expansion. An agent turn ends with a truthful readable outcome, validation and next-step context, not naked tool JSON.
- Scrolling follows latest only when near bottom; show a discoverable Jump to Latest when scrolled away. Reopening/restart restores meaningfully without cross-project leakage.
- Handle long/partial/empty/loading/failed/canceled/recovered transcripts without freezing or marking absent evidence as passed.
- Verify safe Markdown handling: no executable HTML/script, unsafe URL/protocol, remote unapproved embedded image loads, exposed secrets or provider-internal reasoning; preserve source/candidate link guards. A malformed Markdown block must degrade to readable text without injecting HTML.

If a complete transcript renderer redesign would exceed the bounded three-iteration R4 scope, implement only evidence-backed highest-impact reusable fixes, log remaining items explicitly as `c11-work-experience` dependencies and mark the affected R4 usability gate PARTIAL; do not fabricate polished UX screenshots.

### Cycle 3 — Browser usability polish + security regression

Replay the final **real browser** Work → candidate review → transcript → History/Phase Focus → Planning Map/Roadmap journey, reusing source-applicable completed R1–R3 data.

**Usability acceptance**
- Wide and narrow panes (including dock placement changes), accessible keyboard tab/Enter/Space/Escape navigation, readable focus, button labels and text wrapping.
- One clear primary next action with no scattered redundant controls; neutral secondary styling, no orange noise or noisy status badges.
- Loading/empty/blocked/failing/canceled/success/restart states have readable guidance and recovery. History opens actual records and Phase Focus status never fabricates implementation or qualification.
- Selected Work/scroll/focus persists across refresh, backend restart and A→B→A project navigation, without wrong-project artifacts.
- Check light/dark/theme or reduced-motion behavior only where the existing controls support it; do not create unrelated theme work.

**Security-focused regression (mandatory, but no broad reimplementation)**
1. Open prompt, preview candidate, navigate tabs and inspect transcript **without** creating a Work Run or grant.
2. Candidate reject leaves zero authoritative effects; accept stays behind matching grant, validated frozen fingerprint and review control.
3. Missing/revoked grant, unauthorized path, accepted-dirty drift, failed validation, stale prompt source and repeated decision deny safely (use source-applicable targeted existing tests when destructive live repro is unnecessary).
4. Foreign project/owner, stale Roadmap/Planning revision and A→B→A Work/History/Chat separation remain enforced.
5. Sanitized Markdown/links never execute scripts, fetch hidden content, disclose credentials or alter project state.
6. No silent hosted-model fallback, no consent bypass or unauthorized external network calls.

Use real UI negative observations for the highest-risk exposed controls, and focused tests for destructive cases; distinguish them in the evidence matrix. No need to recreate a new paid provider run solely to recheck a previously qualified candidate flow.

## Product outcome and acceptance example

In a clean disposable project already containing a handful of modules, the developer opens the existing ChatPanel and says: "Add a visual Git history. Reuse our existing diff editor; branch checkout and commits should be easy. Keep permissions explicit." The first successful planning response gives **a complete, logically ordered, repository-grounded implementation plan** (goal, genuine modules/evidence, dependencies, steps, acceptance and risks), not one previewed Roadmap create-node operation. The developer replies "drop the separate diff viewer and put checkout under the toolbar"; the same plan draft revises the affected steps without losing unrelated decisions. The plan appears in the existing Roadmap as provisional strategic phases/checkpoints, with details in its inspector. After deliberate review and existing canonical Markdown approval, the developer can select a checkpoint and independently **Prepare Work** using existing Planning Map/WorkItem and executable stack approvals. Nothing auto-executes and no unsupported completion/Green claim is made.

## Implementation topology

`Existing ChatPanel -> ChatBackend planning intent -> bounded read-only ChatProjectGrounder/ChatContextComposer packet -> measured selected model -> completed validated plan proposal + readable prose -> existing durable plan/draft owner (revision/IDs) -> human edit/approve in Chat + same Roadmap canvas -> RoadmapGreenfield/ProjectPlanningActions/source owner -> separately approved canonical linked Markdown -> existing Planning Bridge Prepare Work -> WorkItems/stack preview -> independent approval and Run`.

The **plan draft** is noncanonical. The source-backed canonical Roadmap/Planning Map/Work/History owners remain independent. Reject any design that introduces a second Chat, duplicate full Roadmap truth, unrestricted model commands or implicit project mutation. Carefully distinguish non-model manual draft editing and model proposal actions.

## Explicit product splits and stop conditions

**P1 (draft authority):** Preserve old `GreenfieldDraft` data, known valid persisted schemas and preview behavior. If the required plan payload cannot be backward-compatible, add a versioned migration/read fallback and its tests, with exactly one existing owner. No new canonical `plan.json` with independent copy of Roadmap state. Avoid expanding the existing 512 KiB draft store beyond reviewed limits.

**P2 (read permissions):** Reuse existing source-safe reads only. Any investigatory "tool" is deterministic app-owned read/query, not arbitrary model-generated command or Work ExecutionGrant. A capped gather-and-synthesize loop is allowed if fully observable and cancellable; no background executor or whole workspace dump.

**P3 (model contract):** Use complete JSON schema for plan proposal; the primary user reply displays well-formatted substantive prose, with untrusted machine envelopes behind compact disclosure. Keep original `no-action` contract for regular questions and existing one/2–3 Roadmap action proposal grammar. Dope assigns/reconciles IDs and prerequisites. Complete plan draft creation may use a larger plan schema, but **not** larger atomic Roadmap action rights. Ground step "reused file" claims in P2 packet or label as assumptions. Expose graceful failure if local model cannot fit output.

**P4 (plan revisions):** Developer must be able to say "combine 3 and 4", "use existing module", "add tests" and have a clear diff. The model proposes; Dope applies preview only after developer action. No rewriting already authored source or automatically applying a contested choice. Do not turn editor UI into manual form entry requirement.

**P5 (projection):** Distinguish strategic Roadmap phases/checkpoints from lower-level engineering tasks intentionally left for ADR 0038 Planning Map and WorkItems. Project entire reviewed outline by bounded validated owner calls, with explicit partial-failure recovery or all-or-nothing draft preview, but don't promise cross-owner transaction atomicity. Existing canvas refresh/side inspector and linked Markdown rules must still hold. Source-conflicted plan cannot bypass `Refresh Roadmap`/relink approval.

**P6 (Bridge):** Only *current approved Roadmap checkpoint* is handoff authority, not arbitrary Chat prose or a stale draft step. Reuse current Impact/Target/WorkItems/prompt composer, and surface unavailable Planning Map rather than fabricating readiness. Separate Roadmap, architecture target and executable-stack approvals, Work grant, candidate review and closeout remain. Never reorder already authored P*.txt.

**P7 (cross-system):** Focused integration tests using existing fixture modules. Targeted `npm run build:extension` or package builds when tests import compiled `lib`, focused `node --test` and `git diff --check`. Single final aggregate belongs to P8 (or earlier only if an integration gate specifically requires it). Prompt runtime budgets require narrow fixes, not an overbroad refactor.

**P8 (real evidence):** Actually operate selected Q4_K_M at measured 32768; do not infer model from configured name alone. Record starting/end product commit, dirty fingerprint, bundle hash, local provider connection, measured context, explicit reviewer, real GUI step-by-step observations, source citations/hashes and safety negatives. Record native Electron separately as PASS only if directly observed; an Electron build is not parity. Use a disposable project and safe approvals, no production project writes. If any required gate fails, report NOT GREEN/EVIDENCE GAP, preserve source and do not rewrite old closeouts.

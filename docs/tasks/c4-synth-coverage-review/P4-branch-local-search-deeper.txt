TASK: Correction 4 / P4 — Branch-local Search Deeper review refinement

MODEL / REASONING / USAGE
- Recommended configuration: `GPT-6 Sol High`.
- Browser required: no.

VERSIONING
- Required unchanged project version: `0.4.6`.

VALIDATION TIER / EXECUTION BUDGET
- Tier: **T2 — Integration validation**.
- Target <=8 minutes where practical; 15-minute hard implementation budget.
- This prompt may run focused multi-package UI/backend integration tests, but not live browser/provider/package qualification.

GOAL

Add **Search Deeper** to every pending System and Subsystem so the developer can run bounded targeted synthesis on the current edited branch, preview a replacement/refinement, and explicitly Accept or Reject it without losing unrelated review work.

PREFLIGHT

Read BOOT/AGENTS, ADR 0010-0015, current architecture/product/roadmap/workflow, successful P1-P3 results, and this correction assessment/plan/README.

Inspect exact current review/backend/service/controller/widget state ownership before editing.

Require package `0.4.6`.

ONE REVIEW AUTHORITY

Preserve the existing pending review/draft as the sole review authority.

Do not create a second canonical draft, backend attachment or independent project identity.

Search Deeper works on a snapshot of the **current edited target branch**, including manual rename/reparent/add/remove edits already made there.

TARGET CONTRACT

Add the smallest provider-independent targeted-refinement request/result contract.

It must bind:
- current review identity;
- target proposal key and kind (`system` or `subsystem`);
- parent context where applicable;
- deterministic target-branch revision/fingerprint;
- current edited target branch;
- exact parent evidence packet identity;
- relevant Observed implementation evidence;
- uncovered/cross-boundary coverage cues;
- relevant Documented bootstrap/README/doc context, including `MODULES.md` only when it belongs to the current pending review's source context;
- bounded provider/stage semantics.

Targeted calls must be distinguishable in telemetry/attempt records.

Search Deeper is bounded. It is not recursive autonomous search.

TARGET SCOPE

For a System:
- targeted refinement may replace/refine that System and its descendants;
- unrelated Systems remain untouched.

For a Subsystem:
- refinement may keep/rename/refine/split that Subsystem and its Components inside the same parent System;
- it cannot replace siblings or move content across unrelated Systems without explicit developer editing afterward.

Every proposed implementation boundary still needs source-backed Observed support. Docs remain orientation/support only. Search Deeper must not treat a newly edited `MODULES.md` as an implicit canonical update or silently restart the review from external document state.

PREVIEW / STALENESS

A Search Deeper result is preview state only.

Before presenting/applying it:
- verify review identity still matches;
- verify target branch revision/fingerprint still matches request input;
- reject stale output if the target changed while the call ran.

The developer gets explicit:
- **Accept refinement** — replace only the targeted branch;
- **Reject refinement** — discard preview with no draft change.

Final architecture still requires the existing explicit final acceptance.

UI

In the center review detail panel:
- every System and Subsystem shows **Search Deeper**;
- Component does not;
- show target-local busy/error status;
- preview is clearly distinct from current draft;
- show high-level branch changes without introducing Phase 5 diagrams;
- expose Accept/Reject;
- retain ordinary rename/add/remove/reparent controls;
- evidence sections distinguish **Observed**, **Documented**, and **Inferred**;
- implementation evidence remains source navigable;
- document evidence can navigate/open its repository document source.

Project/root switching must cancel/ignore stale targeted results and clear preview state.

BACKEND / SERVICE

Add typed service operations rather than direct UI/provider coupling.

Reuse current synthesis provider selection/readiness. Do not silently select/fallback providers.

Use deterministic targeted evidence planning; do not send the entire repository again simply because Search Deeper was clicked.

TESTS

Install focused integration regressions proving:
- Search Deeper exists on System/Subsystem only;
- current manual edits are sent in target branch;
- unrelated branches are preserved;
- preview does not mutate draft;
- reject is no-op;
- accept replaces only target branch;
- System refinement may replace descendants only inside target System;
- Subsystem refinement stays in parent System;
- stale target branch result is rejected;
- project switch invalidates in-flight result/preview;
- Observed/Documented/Inferred evidence stays distinct;
- document and implementation navigation resolve safely;
- final canonical acceptance remains separate.

Update `test:product` if new test files are introduced.

T2 VALIDATION

Run:
- focused synthesis/service/backend/controller/widget tests;
- affected multi-package integration tests;
- affected package typecheck/build;
- root/project-switch focused regression;
- `git diff --check`;
- prompt-folder validation if available after writing code.

Do not run real Gemini/Local calls, direct browser qualification, full `npm run check`, restart, AppImage or native launch.

FINAL RESPONSE

Report:
- targeted contract;
- branch fingerprint/staleness rule;
- evidence/doc selection;
- preview Accept/Reject behavior;
- branch-preservation tests;
- integration checks;
- unchanged `0.4.6`;
- readiness for P5.

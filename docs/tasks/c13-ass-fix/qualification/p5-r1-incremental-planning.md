## Changed design and source

- `packages/theia-extension/src/node/incremental-plan.ts` owns bounded `plan_status`, `plan_stage_step`, `plan_correct_step`, `plan_stage_closeout`, `plan_stage_efficiency`, and `plan_finish` behavior. Status returns the Assessment revision/hash, expected count, accepted/missing IDs and accepted hashes, closeout and ten-gate readiness, current Plan revision, blockers, eligibility, and one next action. It does not return the growing Plan.
- `packages/theia-extension/src/node/prompt-draft-store.ts` saves accepted noncanonical partial Plan records through the existing Chat repository transaction and lease. It pins Assessment revision/hash and broker source refs, bounds stored content, rejects stale/foreign state, keeps identical replay idempotent, and requires a hash-bound compare-and-swap correction for an accepted step. A failed correction leaves prior accepted bytes intact. An accepted Assessment revision clears dependent partial and sealed Plans; a rejected Assessment revision preserves them.
- `packages/theia-extension/src/node/prompt-authoring-stage.ts` now instructs Planning to use bounded tools instead of a whole final JSON packet. The existing full `validatedPlan` checks run at finish on the assembled stored records, retaining exact reviewed count/IDs/title/boundary/dependencies, detailed fields, source claims, T1/T2, separate T3 closeout, and all ten ordered efficiency findings. The 128 KiB assembled record limit supports ten substantial steps while each model submission remains bounded.
- `packages/theia-extension/src/node/chat-backend.ts` initializes the Plan only from a trusted selected Assessment and checks active project, Chat turn, owner and lease on every Plan tool call. A successful finish saves one current `PlanRecord`, its dependency hash and source receipts, renders the short Plan card, and unlocks the existing checked `/prompt-write` chip. Final model prose cannot finish a Plan. A failed or cancelled attempt leaves accepted partial steps, previous Assessment, and any earlier sealed Plan intact; resumption must pass the same source and authority checks.
- `packages/pi-runtime/worker.mjs`, `packages/theia-extension/src/node/pi-runtime-host.ts`, `pi-model-bridge.ts`, `pi-conversation-runtime.ts`, `packages/contracts/src/model-runtime.ts`, and `packages/chat/src/index.ts`/`activity.ts` expose only the protected read and Plan tools in the Plan session and preserve safe tool names/outcomes in saved Chat. ## Grounding, finish and diagnostics

Each step cites exact quote text from a successful brokered `read_file` page. Dope verifies unique byte matches and supplies source hash/offset identities; the model supplies neither. Working files and test targets must have been read in that Plan turn. Invented paths, unsupported quotations, foreign source identities, changed source, wrong owner/lease, revised Assessment, changed count/boundary, invalid dependency order, missing closeout/gate, oversized submissions, and premature finish fail without a sealed Plan. At finish Dope re-reads pinned pages, checks current source hashes and full structured Plan validity, then atomically saves the established `PlanRecord` and dependency hash. The saved readable Plan remains a derived projection; Prompt Write consumes that checked record without a whole Plan packet in downstream context.

Known Planning failures now surface a specific safe code in the saved Chat failure or protected tool result: `PLAN_INVALID_STEP`, `PLAN_UNSUPPORTED_SOURCE`, `PLAN_INCOMPLETE`, `PLAN_STALE`, `PLAN_AUTHORITY`, `PLAN_RESOURCE_LIMIT`, `PLAN_INVALID_OUTPUT`, `PROVIDER_FAILURE`, `WORKER_FAILURE`, or `UNKNOWN_FAILURE`, as applicable. Source rejections describe the missing responsibility without exposing file contents or tool arguments. A provider HTTP failure in the real-worker deterministic fixture is saved as `PROVIDER_FAILURE`, after a valid step remains durable. The next authorized turn sees that step in `plan_status`, accepts identical replay idempotently, and finishes without repeating its effect. Generic `Conversation failed` remains possible for unrelated ordinary Chat errors; it is no longer the expected terminal diagnostic for a known protected Planning validation failure.

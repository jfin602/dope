## Prompt

Act as a **new developer unfamiliar with Dope**. Explore the **real Dope browser/Electron application**, trying to accomplish meaningful work, and identify usability friction *we have not yet discovered*. **Do not repair application code**, change dependencies/versions, run an implementation stack, or declare Phase 11 Green.

1. **Preflight:** Record exact project, GUI, Dope source SHA/version/dirty worktree, active model/provider if relevant, actor (human or AI with GUI tools) and previous hunt identifiers. Read the Phase 11 issue ledger, coverage matrix and owner-reported known issues to avoid duplicates and pick under-tested tasks. Confirm live registered widgets; do not assume planned screens exist.
2. **Safety:** Use a disposable project and safe data for negative tests. Do not damage user files, perform real external/paid actions, cross project/provider permission boundaries, send data to unapproved hosted models or commit product changes. If a user task needs dangerous or unauthorized effects, stop that test and report the blocker.
3. **Choose real user goals:** Pick a small coherent group from Roadmap/source changes, saved Chat/context/models, AI Center, Software/Physical/Flow maps, Planning Maps, Work approvals/AgentRun, History and shell navigation. Each task needs a stated expected outcome, not just "inspect this panel".
4. **Use Dope as a person would:** Try primary action and recovery. Test normal/empty/loading/error/read-only/cancel/stale states, wrong files and unavailable resources where safe, narrow panel, keyboard, focus, alternate theme, restart and cross-panel handoffs as appropriate. Note whether it is obvious *what happened and what to do next* without interpreting raw JSON or hidden logs.
5. **Record evidence:** For each task note entry action, exact click/key sequence, expected vs observed result, environment, reproducibility and recovery. Provide screenshots/log references only if captured. Distinguish live GUI observation from owner report, source hypothesis and heuristic guess; do not infer permanent loading from one still screenshot. Preserve previous source-specific Green as historical evidence even when the current candidate regresses.
6. **Triage-only output:** Deduplicate against existing UX IDs; propose stable new IDs for distinct issues, P0/P1/P2 impact, exact reproduction, affected state/task, likely owner, confidence, smallest coherent repair and risks. Explicitly identify unverified root-cause guesses. List **Known issues reproduced**, **New findings**, **Evidence gaps**, **Coverage delta**, **Proposed repair groups**, and **Next different hunt target**.
7. **Stop:** Do not make product code changes or launch fixes. A human/reviewer may reconcile grounded findings into the documentation issue ledger and coverage matrix. Separate /prompt-ass → /prompt-plan → /prompt-write and a later explicit owner Run are needed for any repair. A future manual verification must replay the problem on the exact repaired candidate.

Repeat on **different** under-tested flows, not just the same Roadmap/Chat cases. Two broad clean but materially different hunts are one necessary confidence gate, **not** sufficient without real full-surface coverage, zero unresolved P0/material P1, source-bound regression evidence and owner acceptance.

RESPONSIBILITY SIGNALS

Extend deterministic evidence planning with rebuildable provider-independent responsibility-oriented metadata.

A responsibility signal may group existing evidence by generic cross-layer cues such as:
- recurring normalized semantic concepts across source areas;
- public/HTTP contracts and the implementation that serves them;
- jobs/worker handlers and the behavior/state they operate on;
- explicit state/repository ownership connected to higher-level behavior;
- external delivery/integration boundaries;
- framework registrations tied to meaningful application services;
- dependency communities that connect the same semantic responsibility across presentation/API/persistence/worker planes.

Every signal must:
- be deterministic for identical packet/planner inputs;
- carry a stable derived identity;
- cite only existing parent packet evidence refs;
- preserve source provenance;
- remain planning metadata, never physical/canonical architecture;
- contain bounded compact fields only;
- be safe to include in provider stage context without free-form reasoning.

Do not:
- read project architecture docs to create signals;
- hard-code benchmark terms such as Feed, Delivery, Integration, Opportunity, GA4 or Ahrefs;
- treat filenames/directories as architecture authority;
- create an embedding/vector/LLM preprocessing dependency.

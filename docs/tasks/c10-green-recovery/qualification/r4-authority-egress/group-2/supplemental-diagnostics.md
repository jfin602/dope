## Chrome control and Dope profiles

The `about:blank` control and Dope Chrome network services both sent to public destinations. Their largest destination groups were mapped by each profile's NetLog DNS cache to **candidate** Chromium service hosts such as `optimizationguide-pa.googleapis.com`, `android.clients.google.com`, and `*.gvt1.com`; the Dope profile also had loopback traffic to its local backend. A retained URL-request event named `android.clients.google.com` in both profiles. This supports Chromium background-traffic attribution for shared patterns, but a DNS cache entry alone cannot prove the host used by a connection, especially when addresses are shared. The Dope cache also listed `content-autofill.googleapis.com` on shared addresses, without a retained request event to establish a distinct Autofill transmission.

Both 20 MB caps were reached. Although the requested capture duration was 45 seconds, the files retain only about 28–29 seconds of events; the first roughly 16 seconds of each startup were overwritten. The host trace covers the full capture windows, but NetLog attribution for those earliest events is unavailable. The first blank Chrome launch exited before a log was captured; the same still-disposable profile was relaunched for the bounded control capture. A later reopen of the Dope profile did not start another NetLog.

The reopened Dope Chrome process also sent to public destinations while displaying the disposable local app. Its destinationless `sendmsg` records used FDs 5 and 23; while that process remained alive, both FDs resolved to Unix stream sockets, so these particular records were local IPC. The earlier exited Chrome network-service FDs cannot be retrospectively classified with the same certainty.

This strongly attributes the startup activity to Chromium spellcheck, but no native NetLog ties that exact socket to that exact request or proves its payload. It remains a bounded attribution limit, rather than evidence that the Dope model sent project data externally.

The supported target is the Dope application operated in the Codex browser, its actual Dope backend, and the explicitly selected local LM Studio model. ## Boundary and attribution

The in-scope browser actor is the identified Dope tab and its application requests to the loopback Theia backend. The in-scope server actor is that backend and its model request to the local LM Studio endpoint. Attribute browser activity with tab-specific application URL/request or registered service evidence, correlated to the saved Chat operation and server events. The Codex browser network service is shared with other tabs and Codex itself: a process-level external socket event alone is **neither Dope activity nor proof of its absence**. Classify only requests legitimately tied to the Dope tab. Review the Dope frontend/backend request paths for other possible project-data routes; unexplained *in-scope* requests block the negative assertion.

Independent Chrome profiles, native Electron, unrelated shared-browser traffic, OS services and whole-host traffic are outside this qualification boundary. Their recorded external events are retained and may inform a later desktop/host qualification. They neither pass nor block browser-scoped R4 unless there is evidence tying an event to the Dope tab or backend. No verdict here claims native desktop or whole-host no-egress. Do not infer zero packet loss or comprehensive host transmission coverage from the owner tracer.

## Mandatory assertions

Record PASS / FAIL / EVIDENCE GAP for each assertion, with source, fixture, actor, timestamp and sanitized evidence. Reuse earlier direct observations only where product bytes, producer/consumer seams and fixture meaning remain applicable. Collect only missing evidence.

1. **Actual local selection and inference:** LM Studio loaded `qwen3-coder-30b-a3b-instruct@q4_k_m` at 32768; the saved Dope Chat explicitly selected it, and actual execution provenance identifies the local model. No global model setting changes.
2. **Dope-controlled browser attribution:** identify the Codex-browser Dope tab, its local application request/service path and the saved Chat operation at matching times. Do not assign shared browser traffic to this tab by PID alone.
3. **Backend-to-model locality:** identify the serving Dope backend and contemporaneous request/response communication with LM Studio on loopback `127.0.0.1:1234`, tied to the actual turn.
4. **No unauthorized hosted model fallback:** show selected-versus-actual local provenance for the successful and failed turns, inspect the effective provider selection/fallback paths, and resolve any in-scope hosted model request. A local response alone is insufficient if a separate hosted fallback could have occurred.
5. **No unauthorized Dope-initiated project-data egress:** account for in-scope tab-originated application requests and backend network destinations during the defined turn and controls, including any project-data-bearing request path. A shared-browser socket without tab attribution is not evidence of Dope egress; an unexplained Dope-attributed external request is an evidence gap or failure. State coverage and event-loss limits without upgrading them to a whole-host negative.
6. **Trusted write flow and fresh recovery:** actual model proposal, trusted preview, pending/no-write, explicit manual approval, accepted owner/linked Markdown source change, then a fresh source-grounded turn; record revisions and hashes.
7. **Honest states:** directly observed failed, cancelled and no-action saved-Chat states must accurately reflect execution and leave owner/linked Markdown unchanged when no approval is applied. Reuse source-equivalent denial/restart evidence where relevant.
8. **Source applicability:** compare final product bytes and affected seams against R2, R3 and R4 Group 1 evidence; carry only their proven scopes. Repair and selectively reobserve any invalidated seam.

**Exit:** issue `R4 GREEN / QUALIFIED FOR BROWSER SCOPE` only if all eight assertions pass. Name the desktop, independent Chrome, shared-service and whole-host exclusions explicitly. If any in-scope assertion remains unsupported, continue repair in R4 and do not begin R5. A product defect requires a narrow fix and retest.

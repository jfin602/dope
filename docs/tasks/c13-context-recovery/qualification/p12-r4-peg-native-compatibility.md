## Request and ownership trace

AI Center's local model discovery reads the OpenAI model list and LM Studio's native `/api/v1/models` loaded-instance metadata in `conversational-providers.ts`. `chat-backend.ts` retains the selected connection/model and saved reasoning controls; `pi-conversation-runtime.ts` passes `reasoning.effort` and the resolved output allowance to `PiModelBridge`. The bridge binds the exact refreshed model and loaded context, maps Auto to the provider default (`low` here), and registers a `dope-local` `openai-completions` model with `maxTokensField: max_tokens` and `supportsReasoningEffort: true`. Its physical registration ceiling is loaded context minus 1,536 (14,848 here), further limited by a known provider ceiling. The trusted operation policy and turn set the smaller effective per-call `max_tokens`; the exact failed R3 call allowance is absent from saved evidence.

`pi-runtime-host.ts` opens the isolated worker. `worker.mjs` registers the model with bundled Pi 1.4.0, exposes only the protected Assessment tool schemas, and brokers every tool result through Dope. Pi's OpenAI-compatible adapter serializes chat roles, function tools, tool results, `reasoning_effort`, `max_tokens`, and streaming. It supplies no `response_format` on the observed requests. LM Studio applies its selected Jinja template and its engine parses generated GPT-OSS output. Dope does not select or implement that parser. The worker's safe fetch wrapper records response-header status before consuming the stream; a later stream error can therefore coexist with HTTP 200 headers.

R3 saved evidence shows a **30-message** failed provider request at `reasoning_effort: low`, 92 generated engine tokens, `truncated = 0`, `common_chat_peg_parse: unparsed peg-native output`, followed by LM Studio's `Engine protocol predict stream returned an error` and engine error object code **500**. The saved Dope failure is `model_generation / provider_failure`, subcause unknown, last observed HTTP status **200**. Engine error code 500 is **not** an established HTTP response status. The original P12 log has the same parser/error signature. Neither log excerpt safely establishes the unparsed token shape, exact request body, selected template override, or cause of malformed output. R3's missing `expectedSourceHash` was a separately denied tool request; no causal link to the parser failure is shown.

The installed Pi adapter captures streamed `reasoning` or `reasoning_content` as a signed thinking block and replays its recorded field on the assistant tool-call message. A safe live capture of the second Pi request showed `developer, user, assistant, tool`; the assistant tool-call message included a nonempty `reasoning` field (34 characters) and one tool call. This rules out *complete absence* of reasoning in that synthetic continuation. It does not establish how R3's 14 earlier tool turns were encoded, nor whether LM Studio treats `reasoning` and `reasoning_content` identically in every continuation. A [llama.cpp maintainer's diagnosis of another GPT-OSS peg-native case](https://github.com/ggml-org/llama.cpp/issues/27720) found that omitting reasoning on assistant tool-call replay destabilized subsequent output. That is a relevant hypothesis, not proof for R3. A [separate GPT-OSS parser issue](https://github.com/ggml-org/llama.cpp/issues/31520) documents a different intermittent header form; its reported fix cannot be assumed present in this LM Studio engine or applicable here.

## Failure ownership and action

The **immediate failure** in both historical live runs is an LM Studio/llama.cpp peg-native parse rejection during generation, upstream of Dope's broker. The **root cause** remains unresolved: model sampling, the selected template, accumulated tool/reasoning history, engine parser behavior, or their interaction could contribute. Direct and Pi probes completed, so this investigation did not establish a Dope-owned serialization defect, a reasoning-level-specific failure, or a reproducible upstream failure on synthetic input. One successful synthetic turn cannot overturn the two historical failures.

No product, Pi, parser, template, model, or global runtime configuration was changed. In particular, no parser error was suppressed, no automatic retry was added, and no source-hash or tool gate was relaxed. If further authorized work is warranted, use a **redacted exact failing-request shape and safe malformed-output signature** to compare assistant reasoning-field replay and the active LM Studio template/engine, then check an official supported LM Studio/runtime update in a controlled environment. An update is a candidate, not a verified remedy. Dope should continue saving `provider_failure` and its last observed HTTP status without presenting the engine's 500 as the HTTP status.

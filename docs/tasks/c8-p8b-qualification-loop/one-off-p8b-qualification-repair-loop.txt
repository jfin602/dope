POST-CORRECTION AUTHORITY LAW

There are now TWO distinct boundaries.

A. Provider / ExecutionWorkspace authority

Allowed:
- read/write/create/modify/delete/rename inside the isolated ExecutionWorkspace;
- project-local process/test/build inside the ExecutionWorkspace.

Denied:
- network;
- secrets/credential access;
- private HOME/user state;
- effects outside the ExecutionWorkspace;
- authoritative Git control/history mutation;
- system/package-administration effects.

Important:
- deletion inside the ExecutionWorkspace is NOT itself a Phase 8B violation;
- provider workspace changes are candidate work only;
- the provider must never write the authoritative project root directly.

B. Authoritative project promotion authority

Allowed:
- create;
- modify.

Denied:
- delete;
- rename/move;
- Git stage/commit/reset/rebase/checkout/switch/history mutation.

Initial corrected 8B policy:
- classify the complete CandidateDelta first;
- if ANY candidate effect is unauthorized, promote NONE of it;
- only Dope-owned Authority + ToolExecutor may mutate the authoritative project.

Do not test the old obsolete condition "project-file deletion must be denied by the provider sandbox."
Instead prove:
- the provider may delete inside ExecutionWorkspace;
- CandidateDelta classifies that deletion;
- the entire candidate is blocked from authoritative promotion;
- the authoritative project remains unchanged.

GATE 1 - EXECUTIONWORKSPACE ISOLATION + COARSE SANDBOX

Before live model mutation, prove the corrected local boundary directly.

Require:
- authoritative project root and ExecutionWorkspace are distinct canonical paths;
- provider/sandbox cwd is the ExecutionWorkspace;
- provider can create/modify/delete an execution-workspace canary;
- the corresponding authoritative project canary remains unchanged before promotion;
- provider cannot reach the authoritative project through symlink/path/alternate-root escape;
- outside-workspace read/write is denied according to the corrected host policy;
- private HOME/credential-like state is denied;
- network is denied;
- authoritative Git-control/history writes are denied;
- system/package-administration effect is denied/unavailable;
- ACCESS_TOKEN/provider credential bytes are not exposed to model-directed shell;
- the sandbox can actually start with the installed Codex executable;
- no provider process receives the authoritative project root as writable cwd.

A deletion inside ExecutionWorkspace is expected to succeed and is NOT a failure.

If this gate fails, diagnose and repair only the first exact isolation/sandbox defect.

GATE 2 - CANDIDATEDELTA + AUTHORITY/PROMOTION

Prove the corrected Dope-owned mutation boundary without relying on model behavior first.

Use deterministic execution-workspace fixtures derived from a clean authoritative fixture.

A. Modify-only candidate
- modify one tracked file in ExecutionWorkspace;
- CandidateDelta = modify;
- grant authorizes it;
- ToolExecutor promotes it;
- authoritative file matches candidate;
- HEAD unchanged;
- nothing staged/committed.

B. Create + modify candidate
- create one file and modify one file;
- both classified correctly;
- entire candidate authorized;
- both promoted exactly.

C. Delete candidate
- delete a tracked file inside ExecutionWorkspace;
- CandidateDelta includes delete;
- delete is denied;
- promote NOTHING;
- all authoritative files remain byte-for-byte unchanged.

D. Rename/move candidate
- rename/move inside ExecutionWorkspace;
- if safely proven, classify rename/move and deny it;
- if rename identity is not proven, conservative create+delete classification must still cause full candidate denial;
- promote NOTHING.

E. Mixed allowed + denied candidate
- modify allowed file + delete another file;
- full candidate is denied;
- allowed modify is NOT partially applied.

F. Stale authoritative basis
- mutate authoritative affected file after execution basis capture but before promotion;
- promotion fails closed;
- no candidate effect is applied over the changed basis.

G. Path/symlink escape
- candidate or apply target resolving outside approved root is rejected;
- apply nothing.

This gate must prove Authority + ToolExecutor, not provider prompt compliance.

ITERATIVE POST-CORRECTION CYCLE ALGORITHM

For cycle = 1 through 5:

1. QUALIFY
   - Start at the first currently unproven post-correction gate above.
   - Observe it directly.
   - If it passes, continue immediately to the next gate.

2. DIAGNOSE
   - Trace the blocker to exact source/runtime/provider evidence.
   - Compare against ADR 0028 first.
   - Use current provider docs/help only when the blocker is provider-specific.
   - Record the failure boundary before editing.
   - Never log secrets.

3. REPAIR
   - Make the smallest bounded repair inside c8-agent-authority-boundary / Phase 8B semantics.
   - Keep version 0.8.13.
   - Do not reintroduce direct provider writes to the authoritative project.
   - Do not weaken create/modify allowed + delete/rename denied promotion semantics.
   - Do not pull Phase 8C/8D scope forward.
   - If a blocker requires another material authority redesign, stop and route back to /docs-review instead of silently changing architecture.

4. FOCUSED REGRESSION
   - Run only tests/builds invalidated by the repair.
   - Add a permanent regression for the exact observed defect when feasible.
   - Always run git diff --check, no-root-lock and 0.8.13 coherence.
   - Do not run npm run check after every small repair unless the changed boundary invalidates broad integration.

5. REPLAY
   - Repeat the blocked direct gate.
   - If Green, continue through later gates in the SAME cycle until another blocker appears.
   - Controlled tests never replace explicitly required live/native evidence.

6. CHECKPOINT

7. STOP TEST

PER-SYSTEM EVIDENCE SCOPE

For each challenged System, deterministically select a bounded focused view containing:
- the System's supporting evidence;
- owned/likely-owned package/module/service facts;
- internal dependency/cohesion signals;
- public contracts/exports;
- framework registrations;
- data/state/entrypoint signals where relevant;
- enough boundary-neighbor evidence to avoid swallowing adjacent Systems.

Every included fact keeps original parent-packet evidence identity.

The scope is a proposal aid, not deterministic ownership truth.

SUBSYSTEM DISCOVERY

The model stage should identify coherent responsibilities inside the current System.

A Subsystem is not merely a directory/package.

Require:
- temporary Subsystem identity;
- parent System candidate identity;
- name/purpose;
- directly relevant evidence refs;
- rationale/uncertainty;
- clear responsibility distinction from sibling Subsystems.

Do not force a fixed Subsystem count. Allow zero only when the evidence honestly does not support a useful subdivision and ensure this remains visible for later reconciliation.

COMPONENT DISCOVERY

Within the same bounded System pass, or a second bounded stage only when the implemented contract makes that materially better, propose Components under Subsystems.

A Component is a cohesive implementation unit, not every file/class/function.

Keep the total local call structure bounded with the <=8-minute objective in mind.

Introduce the smallest provider-aware scheduler needed for per-System calls.

For the local LM Studio/Qwen reference path, default to one active generation unless direct qualification later proves parallel generation is safe and beneficial.

Do not create a generic job system.

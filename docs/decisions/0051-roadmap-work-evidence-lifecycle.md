# ADR 0051 — Roadmap-led Work and evidence-backed Phase lifecycle

**Owner decision:** 2026-11-05 (America/Chicago). **Status:** OWNER APPROVED FORWARD DESIGN; documentation only until an independently authorized, qualified implementation. **Baseline:** owner-approved coherent `0.13.0` version-only commit `f908c447819b0e7b07a8e49c91a5898a40bccbe9`. **Detailed contract:** [Phase 13 lifecycle](../planning/p13/roadmap-work-lifecycle-contract.md). **Execution plan:** [p13](../tasks/p13/README.md). ## Scheduling and supersession

The owner's later, explicit 2026-11-05 `/docs-apply + /prompt-plan + /prompt-write p13` and `0.13.0` baseline authorization makes **Roadmap-Controlled Development** the active Phase 13 implementation-plan scope. Preserve LSKM's ADR 0023 requirements as a separately deferred **unassigned successor workstream**, not as deleted or completed, and do not silently claim another numbered Phase or update historical outcomes.

## Decision

1. **Roadmap is the main project entry and monitoring surface.** The center Roadmap canvas is the developer's primary place to plan Phases, initiate approved handoff, observe Work, inspect evidence, review decisions and approve completion. Work remains the full execution/detail surface. History supplies immutable chronology, not a parallel task-completion checklist.
2. **Keep one canonical Roadmap authority.** Reuse project-scoped schema-2 `RoadmapStore`/`RoadmapService`, `ProjectPlanningActions`, typed Phase → Gate → Criterion identities, coverage approval, source protection, historical revisions and linked Markdown sync. PlanningMap → PlannedTransformation → WorkItem and AgentTask/AgentRun/candidate/validation retain their own existing ownership. Introduce checked **links/projections**, not a second status writer or a separate canonical progress database.
3. **Separate planning, execution, qualification and closeout.** User-facing Phase labels derive from independent planning lock, Work execution, evidence-backed qualification and owner closeout facts: `Planning`, `Ready for Work`, `In Work`, `Awaiting Qualification`, `Complete`. Blocked/Failed/Stale/Needs Decision are orthogonal alerts. Rename the displayed historical `Planned` state to `Planning` without converting “has one Gate” into an assertion of adequate coverage. Existing `Unplanned`/missing required Gate meaning remains explicit where appropriate.
4. **Formal Finish Planning.** The developer expressly approves Gate-set coverage and the exact canonical Phase revision/source basis after completeness, dependency, pending-proposal and linked-source checks. Lock normal title/purpose/Gate/Criterion editing and hide pencils/`+ Gate`/`+ Correction` on that Phase while retaining read access and evidence inspection. The lock is scoped per Phase; other Phases remain editable. Merely finishing planning never executes code, awards GREEN or closes the Phase.
5. **Reviewed Work handoff.** `Prepare Work` uses the existing Planning Bridge's source-aware assessment, architecture/PlanningMap transformations, WorkItems and approved prompt/Work grammar. Link each approved WorkItem/run to the exact Phase/Gate/Criteria basis. Creating a Work proposal is not an AgentTask grant, Run approval, canonical adoption or candidate promotion. No model self-approval or new filesystem authority.
6. **Work evidence is the qualification input, not completion authority.** Ingest only attributable, checkable evidence receipts: origin run/tool/validator/human observation, target Criterion IDs, actual result, relevant source and candidate/commit identity, scope, freshness, reviewer where required, and stable immutable receipt ID. Progress and GREEN are **derived** by existing ADR 0040 qualification/coverage rules from current sufficient evidence; task completion, tool exit 0, commit existence, percentage, model text or runner checkpoint alone cannot qualify a Criterion. A passing Work test on an unpromoted candidate does not automatically qualify the accepted project source.
7. **Staleness and amendments are first-class.** A locked Phase may be reopened before execution through reviewed owner action. After Work begins, requirements changes require an explicit reviewable amendment and affected Work re-preparation and evidence requalification; source drift, restored Roadmap structure, coverage change, changed tests and failed/interrupted verification cannot leave stale GREEN. Retain previous evidence and decisions historically; never silently overwrite records or invalidate unrelated Gates.
8. **Owner closes the Phase after verified qualification.** Every required Gate must pass current approved evidence, gate-set coverage must be approved, any exceptions explicitly disposed under ADR 0040 and no blocking condition unresolved. A distinct owner closeout records actual outcome. `Complete` never means merely that Work's last task finished; a waiver never quietly counts as a passing Gate.
9. **Presentation follows semantic themes.** Existing Planned visual grammar becomes Planning. Ready for Work, In Work and Complete have distinct accessible noncolor cues and semantic colors separate from custom Dope accent; do not hard-code arbitrary global color or override non-Dope themes. Locked phases hide editor controls but keep inspector, links, evidence and navigation. No disruptive focus/camera hijack from background Work.
10. **Fail closed and recover.** Protect project/root/owner identity, revision/source/lease, Ask/Allow, explicit Run/grant, candidate review, append-only History and cross-project isolation. Retry/restart/cancel cannot duplicate qualification, self-promote work or silently resume unauthorized execution.

## Delivery and qualification

Use bounded `p13` runner-compatible P1–P9 implementation/integration checkpoints and single **manual P10 closeout**, with no implementation runs authorized by documentation creation alone. Qualify source/revision/identity negatives, exact Work-to-Criterion lineage, actual Work validation and candidate review, stale evidence, crash/restart, live browser UI, owner-native Electron evidence and explicit Phase closeout. Historical failures and owner waivers remain unchanged. No version increment beyond the `0.13.0` baseline occurs until actual authorized prompt execution.

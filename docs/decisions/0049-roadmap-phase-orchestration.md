# ADR 0049 — Controller-owned incremental Roadmap generation

**Owner decision:** 2026-11-03; **tool-loop and visualization refinement:** 2026-11-04 (America/Chicago). **Status (2026-11-04):** APPROVED FORWARD ARCHITECTURE; P1/P2 IMPLEMENTATION CHECKPOINTS RECORDED; NOT FULLY QUALIFIED. **Implementation:** [c12-rm-orch](../tasks/c12-rm-orch/README.md). **Contract:** [Roadmap phase orchestration](../planning/p12/roadmap-phase-orchestration-contract.md). **Baseline:** Dope 0.12.7 as documented; the owner's actual local HEAD and dirty tree must be verified before execution.

## Context and decision

Qwen3.5-9B has demonstrated useful project-aware conversation and bounded individual Roadmap edits. In contrast, full-Roadmap freeform text extraction was inconsistent, strict whole-Roadmap JSON/RM1 requirements caused model stalls or incomplete results, and natural-plan-then-conversion introduced a second sequential inference. Earlier natural plans could be useful, but their output was not a dependable machine-readable canonical structure. These observations motivate a change of architecture, not a guarantee that an incremental approach is already qualified.

**Decision:** Dope provides exactly **one first-class greenfield Roadmap Generation Controller**. It owns one project-bound execution session, chosen model/provider, context budget, serial calls, bounded scope ledger, validation, noncanonical staging, progress events, cancel/failure/continuation states, and final review. It runs **one protected continuous Pi execution** in which the selected model proposes successive **one-Phase-at-a-time native tool calls**. The controller validates and stages each completed tool operation before returning a truthful receipt and permitting the next; for a Phase needing multiple small operations the backend keeps them bounded and serialized. The model proposes content, not format, source identity, approval or qualification. Dope assigns IDs, parent relationships and trusted revision/source/lease basis. A validated Phase/Gate/Criterion is staged under **one existing noncanonical proposal authority** and projected live in the Roadmap canvas. Only explicit owner Apply changes the canonical index and linked Markdown.

## Owner refinement — continuous tool-loop and visible next Phase (2026-11-04; docs only)

**What changed:** A connected transcript showed Qwen3.5-9B completing one `roadmap_phase` tool call and then proposing Phase 2 in the **same Pi execution**. The then-current Chat adapter rejected further calls using a one-operation latch (`!operation`). This proves an overrestrictive tool handler; it does **not** by itself prove Phase 1 was durably staged, that Phase 2 had valid arguments, or that uninterrupted generation would be fast or complete. Preserve P7 NOT GREEN and the exact transcript.

**Forward design:** Replace the one-model-execution-per-Phase scheduler (including independent per-Phase conversation reconstruction) with one **bounded protected Pi agent tool-loop** for each trusted `/gen-roadmap` Chat request. The existing Dope controller owns authorization, expected next-Phase index, selected model, stage/validation authority, scope ledger, resource/deadline limits and completion. Qwen chooses the next `roadmap_phase` proposal through standard native tools; Dope must **validate and commit it to the existing NONCANONICAL stage owner before replying with tool success**. The worker can then continue its original tool conversation to propose Phase 2, Phase 3, etc. One outstanding stage mutation at a time; reject/retry bounded malformed or out-of-order operations without running competing stage mutations or enabling implicit Apply. The final `roadmap_finish` is also a tool operation, accepted only after actual staged-state/source/coverage validation and owner review-lease preparation. Do not create a new writer, direct model mutation channel or another generator, and do not preserve the old per-Phase inference scheduler as an alternative selectable/fallback path after successful qualification.

**Visible progress — two distinct acceptance boundaries:**
1. **Tool-validated and provisionally staged:** As soon as a `roadmap_phase` operation is successfully validated and staged under the single proposal ID, its actual Phase card and nested Gates/Criteria appear in the existing live Roadmap canvas. It may be labeled `Staged · Provisional`, **never** `Owner accepted`, `Planned`, `GREEN` or synced. No waiting for the final assistant answer or entire Roadmap. If the Roadmap tab is inactive, the validated state remains available when the owner opens it; do not steal focus.
2. **Owner approved (Apply):** Only explicit Apply through the existing checked proposal owner turns selected Phases/Gates into canonical accepted Roadmap elements. The canvas then displays those accepted elements using the normal planned/accepted visuals as justified by actual Gates and separate evidence state; linked Markdown/History follow their existing protected rules.

**Loading affordance:** Once a staged Phase succeeds and generation is proceeding, show a **small, clearly provisional `Generating next Phase…` placeholder** at the next position in the existing phase sequence, with a restrained animated pulse/spinner (default accent only on the Dope theme). Do **not** invent a Phase title, ID, Gates, count, percentage, or fake accepted card. The animation is visual-only, asynchronous and droppable: it never blocks or awaits Pi, stage operations, or canvas state. When the next real Phase stages, replace the placeholder with validated data and move the loading affordance forward. Clear/replace it on `review-ready`, `incomplete`, `failed`, `cancelled` or `stale`. Under reduced-motion, use an equivalent static icon/text. Keep user pan/zoom/focus, once-only initial locate, active-tab-only auto-preview, high-contrast accessibility and historical browsing suppression.

**Qualification before broad rollout:** First require deterministic integration proof of two sequential `roadmap_phase` calls and `roadmap_finish` through one actual protected Pi worker session, with stage receipts preceding successful tool responses, two intermediate canvas snapshots and the next-Phase loading state. Include malformed/out-of-order/duplicate tool calls, source/revision/lease change between stages, cancellation/late tool response, tool budget/deadline, provider progress, inactive Roadmap and no-write-before-owner-Apply tests. Then one authorized live Qwen3.5-9B two-Phase test; only after success qualify a full tower-defense MVP Roadmap. Timing/quality are measured, not assumed.

## Invocation — exact user slash command only

The **sole executable entry** to the Roadmap Generation Controller is a **trusted user-authored Chat submission** starting with the exact leading command `/gen-roadmap <roadmap prompt>`. Parse at the Chat command boundary **before any Pi inference**; after normalizing outer composer whitespace, require the exact `/gen-roadmap` token, a whitespace separator and a nonempty trimmed prompt (multiline body allowed). Strip the token before passing the body to the controller, retain trusted user-command provenance, and show usage with **zero controller/inference/stage/write calls** for missing body. Never scan quoted/code/prose content or model/tool output for executable commands. No intent classifier or natural-language routing, no automatic greenfield or Planning invocation, no `/roadmap` or `/roadmap generate` alias, no direct Generate Roadmap button, Work, injected tool/model text, old-format fallback or replay invocation. A retained UI affordance may only prefill the command for the user to submit. Normal Chat/Planning and ordinary `/roadmap` editing are unaffected. The command conveys requested intent, **not** permission to bypass Ask/Allow, project/source/revision/lease checks or final owner Apply.

## Clean cutover — no compatibility generation routes

Retire from executable greenfield generation: (1) response-first freeform-to-Roadmap parsing; (2) monolithic freeform/Markdown or typed whole-Roadmap generation; (3) full-plan JSON envelope generation; (4) Roadmap Markers v1 (`RM1`/`END`) model generation and parsing; (5) the locked natural plan followed by automatic RM1 conversion; (6) model-managed default multi-batch greenfield staging orchestration; and (7) fallback switches, flags, prompts, dispatch branches, obsolete test-only implementations and UI states that keep any of these reachable. No backward-compatibility shim, fallback parser, silent retry through an old format, or second writer/store. Historical reports, authored prompts, snapshots, and already accepted Roadmaps are **not** deleted or rewritten.

Preserve as genuine shared infrastructure, after source inspection: schema-2 RoadmapStore/Service and ProjectPlanningActions, Pi native broker/permissions, source/revision/lease checks, validated typed staging/proposal transactions (including `RoadmapNativeStageOwner` and `stageTypedRoadmapDraft` only insofar as they are general checked owners), saved Chat continuity, canvas editing/granular review, linked Markdown safe sync, append-only History/restoration, existing imported/indexed data, and evidence/coverage/qualification authority. Prune generator-specific helpers from these owners; do not rename dead legacy generators and retain them.

## Behavior and truth

- A single controller owns each **continuous Pi execution** and advances **sequentially at the native tool boundary**, only after validation and successful staging. The model may propose the next Phase after receiving the previous tool result, but cannot advance the authoritative expected Phase index or exceed controller budgets. Never assume a model emits one huge deterministic outline; no whole-plan serialization contract. A bounded per-Phase native operation can create a Phase and associated Gates/Criteria; if necessary, use serial small Gate edits under that Phase.
- Model output and tool arguments remain untrusted. Dope checks required Phase title/objective, Gate title/purpose, at least one observable Criterion where required, consistent parent IDs, duplicates, bounds, source/revision/lease, and staged operation dependencies. Malformed results do not advance. No model self-Apply or generic source-write authority.
- Project scope tracking records explicit requested requirements, staged coverage candidates, unresolved questions/omissions and generation bounds. Structural checks are deterministic; semantic coverage suggestions from a model are **not** proof of completeness. The final review must expose uncovered or uncertain requirements and not silently claim total project coverage.
- The same validated provisional projection feeds the existing canvas in live, asynchronous/coalescible updates. It must never slow generation/tool completion, steal focus, repeatedly recenter, or alter accepted/qualified state. Show actual counts and `Generating/Incomplete/Ready/Failed/Cancelled/Stale`; separate provider reasoning when available from structural progress when unavailable.
- Active-tab-only auto-preview, manual View in Roadmap, owner camera/focus, cancellation, stage expiry and historical-mode protections remain. No speculative percentage or AI-generated GREEN. Interrupted drafts are inspectable but not applicable until freshly validated and dependency-closed for owner review.
- Preserve strict /roadmap editing and explicit /gen-roadmap generation permissions, Ask/Allow and project/root/chat/turn/model/source isolation; no automatic provider switch, no mutation of qualification/evidence/waiver, no canonical/Markdown/applied-History writes before explicit Apply.
- Bound phases, calls per Phase, retries, tokens, wall-clock and stalled runs; stop with useful partial draft. Performance must be **measured**, including time-to-first-validated-Phase and time-to-reviewable-draft, not promised.

## 2026-11-04 observed finish failure and model comparison

The independently recorded Qwen3.5-9B P3 trial successfully staged two Phases, executed `roadmap_finish` and reached review-ready within one protected Pi session (142.9 seconds after command acceptance). Its overall qualification nonetheless remained **PARTIAL / NOT GREEN** due to a failed focused source test and unobserved cases. A later owner-operated GPT-OSS 20B trial reported two completed `roadmap_phase` calls with both Phases visible on the canvas, then two **failed** `roadmap_finish` attempts, the first at roughly 30 seconds, followed by no final assistant response. The observed ~4.1x first-finish-attempt comparison is **not** a successful end-to-end throughput comparison; prompts, exact host settings, backend errors and review readiness were not independently matched or verified.

The architectural decision is unchanged. Diagnose the exact native finish schema, actual tool arguments and backend validation before proposing a narrowly scoped correction. Preserve stage ownership, schema/coverage checks, source/revision/lease and explicit Apply boundaries. Failed/repeated finish calls must yield bounded actionable tool diagnostics and a truthful terminal Chat outcome rather than a blank response; a failed session cannot silently become review-ready or applicable. Do not add model-specific generators, old-format fallbacks or relaxed completion validation. See the [contract clarification](../planning/p12/roadmap-phase-orchestration-contract.md) and [owner observation](../tasks/c12-rm-orch-fix/qualification/2026-11-04-gpt-oss-20b-owner-observation.md). A targeted fix/retest requires separate owner authorization.

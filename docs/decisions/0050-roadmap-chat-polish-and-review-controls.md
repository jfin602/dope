# ADR 0050 — Roadmap review tabs, Chat presentation cleanup, and post-orchestration stabilization

**Owner decision:** 2026-11-04 (America/Chicago). **Status:** APPROVED FORWARD DOCS / PROMPT AUTHORING ONLY; NOT IMPLEMENTED, TESTED OR QUALIFIED by this document. **Product reference:** 0.12.7 (verify local manifest). **Contract:** [Roadmap and Chat polish](../planning/p12/roadmap-chat-polish-contract.md). **Execution:** [c12-rm-orch-polish](../tasks/c12-rm-orch-polish/README.md). **Preserved authority:** ADR 0040/0045/0046/0047/0048/0049.

## Context and evidence

On 2026-11-04 a real Qwen3.5-9B Q4_K_M execution completed two `roadmap_phase` calls and `roadmap_finish` through one protected Pi agent execution in approximately 142.9 seconds. Two Phases, two Gates and four Criteria were staged under one noncanonical proposal. The owner explicitly rejected Phase 2 and its children, accepted Phase 1 and its children, then linked Markdown; the screenshot's final one-Phase canonical index is therefore **correct**, not a dropped Phase. The [P3 report](../tasks/c12-rm-orch-fix/qualification/2026-11-04-p3-connected-browser-closeout.md) remains PARTIAL / NOT GREEN: one source-drift test failed, fixture cleanup was intermittent, ordinary Roadmap Apply did not appear in the History panel, and several UI/browser/native cases were unobserved. This does **not** disqualify the demonstrated two-Phase core behavior or qualify the full tower-defense MVP.

Current source shows `roadmap-proposal-cards.ts` using text-heavy select buttons in Phase, Gate and Criterion content; `roadmap-canvas-widget.ts` renders a text-button proposal bar; `chat-panel-widget.ts` renders a redundant `Tool calls (N)` section outside the reasoning/activity timeline, and sometimes content outside the final response footer. `history-owner-metadata.ts` currently projects reviewed restores but not ordinary accepted Roadmap Apply events into recent Project History.

## Decision — freeze successful generation, polish around it

1. **Do not redesign the successful continuous Pi tool loop.** Preserve `/gen-roadmap` exact trusted user entry, selected local-model reasoning, one Pi agent execution, stage-before-tool-success, single noncanonical proposal, real stage projection, live next-Phase placeholder, owner Apply/Reject, source/revision/lease checks, linked Markdown sync and evidence-bound Gate GREEN. The recorded 142.9-second two-Phase run is a **reference observation**, not a guaranteed performance service level.
2. **Theme-native, icon-only element tabs.** Every eligible selectable proposed Phase, Gate, Criterion and Correction gets one small control tab attached to the element's top-right edge and **protruding above its border**. The tab contains (left to right) selection checkbox, check icon for Apply and X icon for Reject. No words inside the controls. Accessible labels/tooltips and keyboard focus distinguish actions, with disabled/busy states. The tab is a real integrated part of the element and not a detached floating overlay. Preserve right-edge visibility at small zoom, viewport clipping, pointer and keyboard behavior, and nested element ownership. Use Dope action accent only under the Dope theme; use existing neutral semantic theme variables otherwise. No arbitrary hardcoded global orange/green/red fills.
3. **Selections and decisions remain exact.** Selection toggles pending operation(s) using the existing backend operation/dependency mapping. A Phase/group control should make descendant scope explicit in tooltip/confirmation; a child-only decision must never orphan its parent or silently accept/reject unrelated nodes. Icon check/X starts the *existing checked preview*, not a direct canonical write. Preserve individual, selected, Phase group, all-remaining decision semantics and the existing reviewed Confirm/Cancel transaction, source/lease/stale/partial Apply handling. Compact bulk actions may remain as icons with counts/accessible labels in one integrated toolbar; remove repeated large text-button rows and raw operation panels only when equivalent functionality exists.
4. **One Chat activity timeline, no duplicate tool dropdown.** Remove the separate `Tool calls (N)` block, dropdown, heading and duplicate list from normal saved/live assistant Chat rendering. Tool calls must remain inside the existing real reasoning/activity timeline with order, status, arguments/diagnostics only as permitted, durable provenance, playback/reload and copy-with-reasoning. If provider reasoning is unavailable, actual tool events still appear in the activity timeline; removing a duplicate UI must never erase tool evidence.
5. **Response actions form the bottom boundary.** The only normal assistant-message content order is reasoning/activity → final response → one compact authoritative Roadmap proposal/result card (if present) → response footer with copy/info/time. No appended roadmap confirmation paragraph, duplicate decision banner, extra tool list or inline response-info panel **below** the footer. The info control must reveal details via a popover/overlay or an integrated expandable area **above** the footer, without changing copy/keyboard semantics. Update an existing result card rather than attaching new confirmation content underneath the response actions. Real operational errors may replace final content as already required; never hide error truth.
6. **Short, readable Roadmap result.** The compact card shows actual status, changed counts, remaining operations and a View in Roadmap affordance. Keep semantic coverage warnings and model-reported unresolved items available through a single Details disclosure, but do not flood the narrow Chat panel with repeated user goals, long Gate lists or alarming duplicate yellow text. Distinguish staged, review-ready, applied, partially applied, rejected, stale, failed. Generic `Roadmap change applied.` text should not duplicate the same outcome already represented on the result card; use factual accepted/rejected counts and provenance.
7. **History truth.** Project History should show ordinary owner-approved Roadmap Apply changes backed by actual durable revision/operation receipts, with stable identity and actual-effect counts. Do not invent entries for stages, rejected/no-op transactions, or automatically synced Markdown as an additional Apply. Retain reviewed restore entries and append-only source-bound revision records; avoid double count on reload. Qualification/evidence and Gate GREEN remain independently protected.
8. **Stabilize and prune.** First repair the failing source-drift fixture/actual defect and intermittent disposable cleanup with full attribution; then implement History and scoped nonvisual dead-code cleanup through the runner. UI work is **manual only**, after runner stops, with browser qualification for each visible change and an exact-source final browser pass. Never delete or rewrite historical NOT GREEN reports, old prompt bytes, existing accepted Roadmaps, or unrelated Work/Chat behavior.

## Delivery split — runner first, manual UI last

The [c12-rm-orch-polish stack](../tasks/c12-rm-orch-polish/README.md) contains runner P1 test/safety stabilization; P2 ordinary Roadmap Apply History integration; P3 bounded nonvisual cleanup and source regression; and a **single final P4 closeout placeholder**, deliberately manual. Actual UI work is separately authored as M1 Roadmap icon tabs, M2 Chat presentation, M3 final connected-browser validation. Those M*.txt prompts reside under `manual/` so the existing runner cannot execute them. Do not use `--closeout` to auto-run P4. Runner checkpoint commits are not independent qualifications under ADR 0048. All UI prompts have browser validation boundaries and retain explicit P7/P3 evidence gaps.

No product modification, run, model/provider selection change, package version change, status upgrade or GREEN follows solely from this decision.

## Decision

The **Roadmap** becomes the project's primary *strategic* spatial planning workspace. Represent existing phase plans as connected game-map-like checkpoints; corrections are branches and unscheduled **Ideas / Issues** are detached pools. A checkpoint carries a stable project-scoped ID, kind (phase/correction/milestone), title, objective, explicit ordering and dependencies, typed links to phase documents, issue/idea records, Planning Maps/WorkItems and evidence-backed gate/closeout status. Node position, viewport, colors and selection are presentation state. Never mark a checkpoint Green solely because a path is filled, an AgentRun ended, or AI says it is done. Preserve historical Not Green, waiver, deferred and unknown evidence.

Checkpoint selection/editing uses the existing **Software Map-style in-place left details inspector**, never a standalone checkpoint detail page. Keep a reusable project-grounded saved **ChatPanel** dockable alongside the center Roadmap (ordinarily right), as with Planning Maps. The Roadmap answers *where and why*, the Software Map answers *what exists*, Planning Maps answer *what architectural changes are proposed*, and History answers *what happened*. Roadmap is not another manual Development Session or task database.

## One state, independent owners

Existing Markdown roadmaps/phase plans, Project Mind Notes/Ideas/Questions/Decisions, project issue registries, Planning Maps/WorkItems, canonical Architecture, agent/validation evidence, Chats and History remain independent data owners. Retire only the separate **Project Mind navigation surface**, after durable knowledge access/recovery is preserved. Unsequenced Issues/Ideas can be promoted/linked without copying their records. History stays a read-only owner-backed activity projection; Planning Maps retain architectural-basis/rebase/adoption authority and cannot be silently rewritten by Roadmap positioning.

A versioned project-local structured Roadmap store/index beneath `.dope/` may own stable checkpoint identities, semantic edges and explicitly roadmap-owned fields/links. Establish **exactly one writer for each editable field**: a validated lossless Markdown round-trip adapter where supported, or structured state with an external source reference. Existing unsupported Markdown stays read-only until safe explicit import/ownership mapping. Never introduce two independently editable versions of phase prose, delete existing Project Mind records, or claim cross-store distributed atomicity.

## Shared human / AI editing contract

Provide a small provider-neutral `ProjectPlanningActions` boundary: selected checkpoint/neighbor/linked-record reads, deterministic previews, typed semantic changes (create, edit, link, reorder, promote idea/issue, propose a Planning Map transformation). Manual inspector/drag gestures and model proposals invoke **the same** Dope-owned validated operations. Bind every request to project-root identity/opaque handle and expected owner revision (plus Planning Map basis/map revision when applicable). Validate schema, identities, dependency cycles, lifecycle, permissions, adoption constraints and referenced owners deterministically. An owner commits its own operation atomically; cross-owner steps must report partial outcomes explicitly rather than pretending to transact across stores.

Commits publish bounded affected object IDs, owner revisions and factual change summaries. Canvas, inspector and other subscribers update immediately; the AI **next step** receives fresh selected-object context. An already-in-flight model cannot absorb external edits into its generation; stale proposals must reject and re-read instead of overwriting manual work. Support revision-safe undo for eligible non-destructive operations; destructive/broad restructuring, adoption, closeout and ambiguous conflicts require explicit preview and developer approval. Model text/JSON is **untrusted proposed action data**, never direct project mutation or proof.

Ordinary Chat planning tools do **not** inherit Phase 8 agent shell, filesystem, process, MCP, network or code-promotion grants. Model proposals go through Dope's own authority service; direct writes to Markdown/JSON by the model are prohibited. ADR 0035's Codex subscription ordinary Chat Responses transport **remains tool-free**; a future Dope planning orchestration layer may validate *completed* conversational output outside that provider transport. Work and CandidateDelta promotion remain separate.

## Local-model-first is a release gate

All Roadmap and Planning Map manual operations work with **no AI model**. A small local model must accomplish supported conversational planning using compact selected-object/neighborhood context and narrow on-demand reads, one short validated action at a time. Do not require loading the whole repo/roadmap/old chats or native provider function-calling. Prefer native structured tools where supported but **require** a strict JSON/constrained-output, schema-validated fallback for runtimes lacking tool APIs. Dope, not the model, computes identity, dependency topology, state transitions and graph invariants.

Qualify a **4,096-total-token context profile**, including output reservation and instructions, where a model supports it; use measured/verified capability limits, never guessed capacity. Bound retries, cancellation, malformed output and context omissions; failures are non-mutating and visible. Local-only means **no silent hosted fallback, egress or background hosted inference**, even on retries; explicitly selected hosted models still require contextual project-data consent and actual model provenance. Provider configuration/capacity is application state, never roadmap truth.

## Presentation

Use center checkpoint map, meaningful branching and visually detached pools, with accessible keyboard navigation, full readable checkpoint identities and left details inspector. The ChatPanel may remain visible in a right/other dock; narrow and resized panes retain usability. Use the **current October 12 Dope Dark restrained-orange** semantics (ADR 0016): neutral dark surfaces/utility controls, brand orange only for intentional active selection/primary action, independently meaningful gate/diagnostic colors, visible subtle keyboard focus, non-color cues and alternate-theme isolation. Brand literal colors belong only in central semantic theme tokens. Preserve independent chat/map color choices.

## Forward clarification — 2026-10-12: existing ChatPanel only, placement-independent planning

**One Chat system, available everywhere is a hard Phase 10 architecture constraint.** Roadmap, Planning Map, Software Map and ordinary project conversations use the **existing** `ChatPanelWidget`, `ChatPanelController`, `ChatService`, `ChatRepository`, `ChatOpenOwners` / backend leases, AI model routing and `.dope/chats/`. Extend their existing typed context composition and Chat turn orchestration with validated project-planning capabilities. **Do not** create a Roadmap-specific chat widget, parallel conversation service/store, saved-chat format, duplicated chat controller, or a new Chat/Planning mode or agent thread. The new `ProjectPlanningActions` is a shared project-domain service used by both manual controls and existing Chat, **not** another chat runtime or panel.

Planning capability is independent of **left/right/center/bottom** panel placement. The model, saved Chat identity, permissions, current project and user-controlled context determine eligibility, never a special right-sidebar widget. All Chat panels retain Select Chat/Chat, normal folders/colors/settings, transcript and streaming, per-message model selection, existing single-owner focus/leases, cross-window/project isolation, restoration, and the same context preview/consent. Moving/reopening a Chat must not create duplicate writers or fork messages.

Opening/focusing a Roadmap, Planning Map or Software Map **must not** auto-create, move, replace, reset, select a different conversation in, or steal focus from an existing ChatPanel. The developer controls the layout and whether Chat is open at all; the center editor, diagrams and planning canvas must remain available. Left/right/bottom Chat and a Chat in an editor-like **center tab/split** are supported through ordinary Theia shell placement; center split behavior must be verified directly rather than assumed. The inspector's left default must not prevent a developer from placing Chat there; handle docking conflicts through ordinary user-managed layout, not a hard-coded 3-column composition.

Contextual grounding belongs behind the current `ChatContextComposer` / `ChatBackend` seam and future Dope planning action orchestrator, not in a canvas-specific ChatPanel or provider adapter. Add bounded typed `roadmap-checkpoint` / roadmap references alongside existing Planning Map and WorkItem context where needed, reusing normal token budgeting, source preview, revision/provenance checks and hosted consent. Active-selection **Follow** and explicit **Pin** (including the selected checkpoint/Planning Map) must be legible and user-controllable; pinned context remains stable across unrelated tab changes, and a follow selection is re-resolved against the currently active project before the next turn/action. No silent retargeting of pending actions; stale revisions and cross-project context reject. Do not mutate saved Chat identity/settings just because canvas focus changed.

**Additional Phase 10 acceptance gate:** take a real saved Chat and use the same planning-action capability from left, right, bottom and center ChatPanels, with the roadmap/editor still usable (including center split when offered by the shell). Reposition/restore it without conversation or model state loss, duplicate writers, chat auto-launch, mode fork or forced editor replacement; verify selection follow/pin, manual map changes reaching the next AI step, project switch, stale proposals and no hosted fallback. Later Phase 11 human usability review may refine presentation but must not defer this Phase 10 correctness gate.

## Forward amendment — 2026-10-12: persistent linked Roadmap and creation

**Approved design; not implemented or qualified.** P16 remains NOT GREEN at committed `0.10.16` source `27ab84e2aaf424b17e1d90ccc5016f8af858661f`. This amendment defines a bounded Phase 10 correction; it does not rewrite historical P1–P16 prompts/closeout, advance versioning, owner-close Phase 10, or activate Phase 11/12.

**Initialization choices.** A Roadmap without accepted state offers visible **Import existing Roadmap**, **Plan with existing Chat**, and **Create manually**. Opening a workspace never silently initializes it. Discover bounded project-root-local Markdown candidates (not only Dope-shaped files); let the user choose a file. Deterministic parsing of headings, phases, milestones, corrections, checklists and provenance produces a draft/preview. Duplicate headings, ambiguous status and unsupported prose remain visibly read-only until manually resolved, never guessed. Optional local model interpretation of a selected section is explicit, not required.

**Persistent document binding.** Acceptance links the structured Roadmap to a human-readable Markdown document; an existing file remains where it is. Record canonical project-relative path, fingerprint/source revision, stable checkpoint ID-to-section mapping, last reconciled basis and link status under `.dope/`. Greenfield planning uses **the same saved ChatPanel, ChatService, ChatRepository, ChatContextComposer and ChatBackend** with short incremental typed proposals accumulated in a noncanonical draft; only explicit approval creates a new Markdown roadmap at a user-approved unused path and accepts the structured state. A model-free manual path remains fully supported. Never overwrite an existing file.

**No competing truth.** Supported mapped titles, objectives, order and planning prose are owned by the linked Markdown; `.dope/` owns stable identities, semantic dependencies, typed links, graph/UI metadata and sync bookkeeping. All mapped-field edits from the UI or Chat travel through existing `ProjectPlanningActions` and the Dope-owned document adapter as one logical authorized edit; the model never gets filesystem grants. Unsupported sections stay source-owned/read-only. Project Mind, Issues, Planning Maps/WorkItems, Architecture, Chat and historic owner-close/qualification evidence retain independent ownership. A checked box or model claim does not establish Green.

**Deterministic bidirectional reconciliation.** Detect source edits with bounded watchers plus checks at focus, refresh, edit and restart. Compare source fingerprints, checkpoint section mappings, Roadmap revision and last synced basis before any write. Apply unambiguous external changes to structured projection, and only minimal source-aware patches (preserving unrelated Markdown, formatting and line endings) for approved Dope changes. Stale/overlapping changes, source moves/deletion, ambiguous mapping, symlinks/out-of-root paths, malformed content or broad destructive edits fail closed to visible diff/relink/review. Never silently overwrite. The document and `.dope/` have separate atomic writes, not a distributed transaction: a recoverable pending-sync state represents interruption, partial success or crash until reconciled. No automatic LLM call is needed for synchronization.

**Authority, scope and gates.** A normal Chat turn remains tool-free except for validated, approved planning proposals dispatched by Dope. No shell, Git, AgentRun, code promotion, hosted inference fallback or implicit project-data egress. Only the explicitly linked roadmap's mapped planning fields participate; Phase 12 semantic cross-repository documentation alignment remains inactive. Qualify actual visible import/create, real source round-trip and external edits, conflict/crash/restart recovery, historical Phase 6/7 gate accuracy, local 4,096-token conversational planning, human approval and next-turn freshness, wrong-project/stale/foreign denial, same saved Chat left/right/bottom/center with center split, independent hosted-egress observation and direct browser/Electron GUI. A passing build alone is not Green.

## Forward amendment — 2026-10-12: runner-aware checkpoints and interactive Roadmap canvas

**Approved design only; Phase 10 P16 remains NOT GREEN at committed `0.10.16` / `27ab84e`.** This amendment combines automatic prompt discovery with an immersive canvas as additional scope for the previously approved `c10-roadmap-create-sync` correction. It does not implement either feature, create another runner/Chat, rewrite historical P1–P16 prompts or closeout, bump versions, owner-close Phase 10 or activate Phases 11/12.

**Auto-detect work conventions without a model.** Once a project's Roadmap is initialized, discover task stacks in the configured in-project task directory (default `docs/tasks/`) using the same exact runner grammar and read-only discovery conventions as the existing Codex phase runner/Work Prompt Stacks. Supported folder forms are historical `p<number>`, pre-1.0 continuation `p<number><letter>`, post-1.0 `p1-<phase>`, post-2.0 `p2-<phase>`, and corrections `c<phase>-<lower-kebab-slug>`. Valid prompt files use `P<number>-<lower-kebab-slug>.txt`. Reuse or extract a shared pure implementation of `scripts/codex-phase-core.mjs` `parsePrompt`/`buildPlan` rules (TASK identity, prompt ordering, version policy, sole closeout and browser/manual requirement); **do not implement a looser second parser in Roadmap UI**. Filename/folder matching alone does not validate the stack or authorize execution.

**Project source-backed child nodes.** A valid phase stack yields sequential **prompt checkpoints** nested under the strategic phase; continuation slices remain identifiable segments of the same phase, not duplicate parent phases. A valid correction creates a separate branch with its own prompt/checkpoint sequence. `c<phase>-...` indicates the parent phase only: link a correction to an exact failed prompt only with explicit typed provenance, never guessed from name/order. Ambiguous/unmatched records remain reviewable in an unlinked-work pool. Historical, superseded, incomplete, malformed and manual one-off files remain clearly labeled non-executing source references rather than silently treated as runnable stages. Persist stable project/stack/prompt identity and checked in-root file links/fingerprints; preserve identity through unambiguous renames and show broken/unsafe references as unresolved. Re-detect on relevant source changes, refresh and restart with bounded cost. **Task files, Work/runner/Git events and qualification closeouts remain independently owned**; linking them does not write into `ROADMAP.md`, create AgentTasks or imply Green.

**Prompt navigation, not invocation.** A single click selects a prompt or phase and updates the existing Software Map-style left inspector. Double-clicking an individual prompt opens its exact `.txt` in the **ordinary Theia editor**. Keyboard Enter on a focused prompt and an **Open Prompt** inspector action are equivalent accessible navigation paths. Missing/moved/unsafe files offer visible recoverable relink feedback. Double-click, Enter, selection and import **never run a prompt**. Future execution must pass through separately authorized Work/AgentTask/runner controls and an explicit developer decision.

**Replace list with a genuine interactive map.** The current `RoadmapCanvasWidget` vertical HTML ordered list is not the required product UX. Replace that presentation with a full-available-area spatial `@xyflow/react` canvas reusing Software Map pan/zoom/focus/control patterns; retain the existing Roadmap projection, store, planning actions, left inspector and independently dockable saved ChatPanel. Background mouse drag and one-finger touch pan; pointer-centered wheel/trackpad zoom and two-finger pinch zoom; offer Zoom In/Out, Fit Map, Focus Selection and usable keyboard alternatives. Dragging a node must not accidentally change semantic order/dependencies; when custom placement is enabled it uses an explicit **Arrange** affordance affecting presentation only. Keep viewport, expansion, coordinates and layout out of canonical domain state, with stable project-scoped restore on refresh/restart, split and resize.

**Three levels of semantic zoom, one stable graph.** World/distant level: phases, milestones and major correction paths; phase/mid level: continuation segments, correction lanes and collapsed prompt stacks; checkpoint/near level: individual prompt nodes, full readable titles, status/evidence and editor links. Smooth changes in semantic detail never change identity, authority, status or Chat Follow/Pin context. Provide explicit expand/collapse/focus that works without a specific zoom level. Deterministic stable branch layout keeps unrelated nodes from jumping; honor user placements. Detached Ideas/Issues remain separate spatial pools. Correction routes do not automatically rejoin as Green. Bound rendering for hundreds of prompts through progressive disclosure and keep selected labels readable rather than truncated.

**UI and qualification gate.** Use current restrained dark-orange tokens (orange for active/action only), meaningful text/icon qualifications, dark/light theme, touch-sized targets, keyboard focus, screen-reader labels, narrow editor and normal center split with **the existing ChatPanel**. Qualify runner-parity discovery over phase/slice/correction/version families, ambiguous/one-off/superseded/missing/foreign cases, stable IDs, safe double-click/Enter with no execution, pan/touch/pinch/wheel/focus/fit, Arrange separation, world/phase/checkpoint zoom, branch truth, large graph responsiveness, persisted viewport and center split. Re-run direct browser and native Electron UI gates alongside previously approved Markdown synchronization, small local model planning, approval/egress and P16 historical status repairs. The missing live evidence remains NOT GREEN until independently qualified.

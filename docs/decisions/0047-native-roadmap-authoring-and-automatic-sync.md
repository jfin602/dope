# ADR 0047 — Native Roadmap authoring, granular review and automatic Markdown synchronization

**Owner decision:** 2026-11-02 (America/Chicago). **Status:** OWNER-APPROVED FORWARD DESIGN / DOCUMENTATION ONLY — NOT IMPLEMENTED, RUN OR QUALIFIED by this decision. **Baseline:** Dope 0.12.7 is the documented reference, not a claim about the owner's local checkout. **Detailed contract:** [Native Roadmap authoring](../planning/p12/native-roadmap-authoring-contract.md). **New correction:** [c12-roadmap-native-authoring](../tasks/c12-roadmap-native-authoring/README.md).

## Problem

The owner observed a tower-defense Roadmap where Chat held a multi-phase checklist with apparent Gates, while the actual center-editor Roadmap showed accepted Phase cards as **Unplanned** with **no accepted Gates**, unresolved objectives and a large "Linked Markdown · Approval required" editing form. An incomplete-definition error prevented acceptance. The screenshot proves a user-facing generation/representation gap, not the specific internal root cause. Actual local source and transaction logs must be inspected before implementation.

Response-first parsing of assistant prose is too weak a boundary for the canonical schema-2 Phase → Gate → Criterion graph. A separate Markdown editing form duplicates the spatial Roadmap editor. Existing all-or-nothing proposal review cannot selectively accept individual items, Phase groups or subsets without losing atomicity or source safety.

## Decision

1. **One Roadmap authority.** Keep the existing project-scoped schema-2 RoadmapStore/RoadmapService, ProjectPlanningActions validation, typed Phase/Gate/Criterion/Correction grammar, saved ChatPanel, Pi broker/tool and permission boundaries. Do not create a parallel writer, snapshot store or model-facing filesystem channel. Canonical structured Roadmap state is authoritative for planning; the linked Markdown is a synchronized, source-protected representation, not the generator of canonical AI changes. Preserve independent qualification/evidence authority.

2. **Typed native AI authoring instead of response parsing.** AI-generated creation and mutation use brokered Roadmap read/stage/preview/apply-or-decide/cancel operations with a versioned bounded schema. Human-readable Chat answers explain proposals but are never parsed to create authoritative Phase/Gate/criterion mutations. Existing freeform planning/read-only answers remain possible; they cannot silently become writes. Local models may stage bounded batches in a single noncanonical proposal, with partial-generation and validation errors reported truthfully. No model or tool can self-approve.

3. **Canvas-first manual editing.** Replace the large Roadmap editing/Linked Markdown panel with the existing Roadmap center-editor as the direct editable surface. Small pencil actions next to supported titles, objectives, purposes, criteria and correction fields invoke inline single-field editors with save/cancel, accessibility, permission and revision checks; richer controls for relations and dependencies may be contextual. The saved ChatPanel remains the conversational authoring entry. Both use the same protected backend mutation service, not a second UI-only owner.

4. **Granular proposal review.** A staged proposal contains stable operation IDs, entity IDs, typed before/after changes, dependency edges and current project/source/revision identity. Developers can apply/reject one operation, explicitly act on a Phase-and-descendants group, apply/reject selected operations, or apply/reject all *remaining pending* operations. Already rejected decisions are not silently included by Apply All. Preview only validated subsets; apply a chosen subset atomically as one revision with one actual-effect receipt. Partial application advances the revision and requires fresh validation/lease for any remaining changes. Rejecting a Phase cannot orphan approved Gates; explain blocked dependent actions or require explicit cascading selection. No silently invented reparenting.

5. **Review in the existing canvas and Chat.** The same backend-validated noncanonical preview drives provisional Phase/Gate/criterion visuals on the Roadmap and the single persistent proposal card in the originating saved Chat answer. Inline canvas decisions and Chat decisions address the same proposal/operation IDs and backend authority. Provisional items never count as accepted, planned, published or qualified. Respect active-tab-only automatic preview, manual View in Roadmap, focus/camera isolation and historical browsing suppression.

6. **One-time destination, then automatic Markdown sync.** During *initial* Roadmap creation, ask for a safe project-local Markdown path and one confirmation to create/link it. After successful manual edits or accepted AI proposals, automatically enqueue deterministic, revision-bound Markdown sync without repeated publication or editor forms. Keep canonical revision commit and sync outcome distinct: pending/conflict/failure is visible and recoverable; never claim synced until bytes, mappings and hash are verified. Preserve unrelated prose and external edits through current source-aware checking, never blind overwrite, outside-root/symlink traversal or model-authored Markdown. Initial file collision requires import/link or alternate path, never overwrite. Existing accepted unlinked drafts retain an explicit first-link action, not a retroactive silent write.

7. **History and qualification remain protected.** Integrate each successful applied subset/bulk transaction with durable append-only Roadmap revisions and real-effect History; rejects/no-ops/failed-zero-effect decisions have no applied History entry. Retain ADR 0046's read-only historical Undo/Redo and reviewed restoration creating a new head; no destructive rollback, second quick-Undo authority or silent reversal of later edits. Evidence, qualification, waivers, coverage completeness, Work grants and executions are never mutable via ordinary inline edit or AI generation. A Phase needs accepted Gates and separate explicit Gate-set coverage approval; only evidence can qualify Gates/Phases GREEN.

8. **Alpha migration, permissions and protection.** Preserve protected current-turn /roadmap authorization for AI-generated accepted-index mutations, independent manual editing and existing explicitly approved greenfield routes. Imported/external Markdown changes keep their own reconciliation boundary. Do not silently promote untrusted response bullets to Gates, silently fallback to legacy schema-1 writers, or reinterpret historical qualifications. Make unsupported operations visible and fail closed.

## Owner refinement — live provisional construction (2026-11-03; docs only)

The owner requires **visible construction during the actual local-model Planning turn**, not merely a complete Roadmap appearing after the final model answer. The authoritative Pi broker may accept efficiently sized, versioned `roadmap_stage` batches; do **not** force one model tool call per Phase, Gate or Criterion. After **each successfully validated batch**, the existing backend proposal owner exposes its latest bounded, server-validated **noncanonical** Phase → Gate → Criterion projection to the active Roadmap canvas. New Phase cards and nested Gates/Criteria appear as verified work is staged. The projection is updated incrementally under one proposal identity; do not create per-batch Chat proposal cards, a shadow Roadmap store, or a response-prose parser.

Preserve the existing **active-tab-only** rule for automatic display. The first eligible live projection may locate the proposal **once**; successive batches update the same overlay without repeatedly fitting, panning, selecting, switching editor tabs or stealing focus. The user can pan, zoom, expand and inspect while the model runs. An inactive/closed Roadmap must not be auto-opened; explicit user navigation can opt into the current validated projection. These presentation updates are asynchronous and coalescible/droppable, and must not delay model generation, broker calls, canonical writes or linked-source sync. Honor reduced motion and accessible, truthful progress.

Show actual validated Phase/Gate/Criterion counts and `Generating / Incomplete / Ready for review / Failed / Cancelled / Stale` states, never speculative percentages or accepted/qualified progress. A partially staged plan is **not** an approved Roadmap and must not expose enabled Apply controls merely because a few valid objects appeared. The one final saved Chat proposal card remains the review entry when the backend marks a dependency-closed draft ready; every Apply still requires explicit owner decision and source/revision/lease revalidation. Cancellation removes live approval authority and provisional ghosts; a bounded inert diagnostic/inspection record may remain, but no canonical Roadmap, Markdown, qualification or applied History effect occurs.

The observed [2026-11-03 P10-A connected Chrome baseline](../tasks/c12-roadmap-sync/qualification/p10-a-connected-chrome-baseline-2026-11-03.md) is **NOT QUALIFIED**: revision-zero native staging reached argument/unsupported-kind/stale-source errors and produced no proposal. Repair exact discoverable action schema, revision-zero `null`/source fingerprint comparison and bounded actionable error recovery **before** qualifying live UI rendering. Require deterministic staged-batch/source/no-write tests plus a real selected-local-model tower-defense Chrome turn that visibly builds the graph before the final response; preserve native Electron's separate owner-evidence boundary. This refinement is **requirements only**, not code, runner execution, prompt retro-editing, or GREEN.

## Forward owner refinement — fast greenfield generation and canvas-only review (2026-11-03)

**Supersession:** This owner-approved direction replaces the previous **default multi-batch model orchestration, mandatory intermediate canvas updates, and duplicate Chat/canvas Apply/Reject interface** for new Roadmaps. The earlier native tool protocol, live-stage design, and R4 qualification reports remain historical and their implemented security protections stay in place until a tested successor is ready. The successful two-Phase/two-Gate native staging demonstration does not establish full tower-defense coverage or competitive generation speed.

**Fast generation:** For a new or uninitialized Roadmap, prefer a single complete **typed strategic proposal** containing ordered Phases with objectives and nested Gates with observable Criteria. Dope—not the local model—attaches the trusted project/Chat/turn/source/revision basis, assigns stable IDs, resolves operation/dependency links, validates completeness and converts the result into the **existing noncanonical proposal and granular transaction owner**. The model should not manage low-level action kinds, UUID aliases, repeated expectedStage calls, or source hashes for normal creation. Preserve current /roadmap authorization, Ask/Allow, no model self-Apply, single RoadmapStore, linked Markdown checks, durable History and qualification/evidence separation. Existing strict typed proposal parsing may be reusable; do not mistake the old response-to-Markdown extractor for canonical write authority. It may be benchmarked as a **validated candidate generator only**.

**Canvas is the sole normal decision surface:** Present proposed Phases/Gates/Criteria as real nested Roadmap elements. Select individual elements or a Phase with its checked descendants, edit provisional fields inline, and Apply/Reject one/selected/all remaining using one small integrated canvas toolbar and the existing backend review. Remove the floating raw-operation panel and duplicated Chat Apply/Reject buttons **only after equivalent canvas review is implemented and qualified**. Show internal action kinds/IDs only in optional diagnostics; preserve true edit/removal diffs. Chat keeps one compact stable progress/ready/terminal summary, actual counts, warnings and **View in Roadmap**—no second normal approval UI. Existing non-Roadmap publication/command approvals retain their independent safeguards.

**Progress without added waiting:** Show validated provisional substructures only when available without extra model calls or latency. Otherwise display honest generation status until the full draft is ready. Do not require multiple stages or two intermediate canvas updates merely to animate construction. Bounded continuation is allowed for measured output-size limits, with explicit incomplete/error states and no endless retry. Keep active-tab-only auto-preview, manual View, camera/focus isolation, accessible controls, expiry/cancel/stale guards and zero canonical/Markdown/History writes before owner Apply.

**Benchmark first:** In repeated matched trials with the **same original tower-defense prompt, selected model/context and disposable fixtures**, compare native multi-batch generation, previous response/extractor-to-reviewed-candidate, and one-pass typed proposal. Measure time to first useful result and complete review-ready draft, token/tool calls, retries/failures, Gate/Criteria counts and completeness, all required MVP mechanics, and explicit approval/no-write safety. The reported approximately one-minute earlier route is a reference, not a measured current benchmark. A faster incomplete Roadmap is not a win. Qualify the chosen fast default in real connected Chrome before shipping.

**Delivery:** baseline comparison → typed generation using the existing owner → canvas-only review/Chat summary → exact-source selected-local-model Chrome qualification. Hold unexecuted `c12-rmr-man/r4-r` follow-on prompts for reassessment rather than continuing obsolete UI polish. Keep original R4 NOT GREEN records, current working source and manual/native Electron evidence separate. This documentation change authorizes no code execution, new prompts, version change or GREEN.

## Latest owner refinement — strict compact Roadmap markers (2026-11-03; docs only)

**Supersession for greenfield model output only.** The owner now prefers **Roadmap Markers v1**, a small deterministic text grammar, over the previously preferred verbose whole-Roadmap JSON model envelope. This **does not reinstate arbitrary freeform Chat-prose extraction**, alter schema-2 canonical storage or weaken the checked native proposal transaction authority. The model describes Phases, Gates and testable Criteria once; Dope parses the complete result into the existing **untrusted typed candidate** and uses the current F3 `stageTypedRoadmapDraft` / `RoadmapNativeStageOwner` to assign identities, build noncanonical operations and require explicit canvas Apply/Reject. Preserve existing F4/F5 canvas/Chat work, protected /roadmap, current project/Chat/turn/lease/revision/source checks, no-write until Apply, safe linked Markdown and independent evidence-bound GREEN.

**Grammar:** A complete response is exactly `RM1`, then ordered `P|title|objective`, `G|title|purpose`, and `C|observable expected result` lines with one final `END`. A `G` belongs to the preceding `P`; a `C` belongs to the preceding `G`. Dope derives a stable, non-invented display title for each Criterion from its one observable-result sentence; the full sentence remains its `expectedResult`. Model outputs no nested JSON, identifiers, revision/source fields, status, dependencies, qualifying evidence, tool calls or final prose. Initial v1 has **no dependency markers**: left-to-right Phase order is presentation chronology, not an inferred semantic dependency. Strict version/header/terminator, field counts, unique titles/results, required nested content, safe text/length, bounded size and complete model finish validation fail closed. Do not ignore malformed lines or turn truncated reasoning/partial text into an approvable proposal.

**Budget and latency truth:** Repeated JSON keys and formatting likely impose avoidable output overhead, but the F6 typed generation failure's exact provider stop/usage cause was unobserved: a 2,048-token reservation and reasoning-only output are not proof that JSON syntax alone caused it. Record provider finish reason and actual reasoning/final usage when exposed, and identify absent measurements. Use only supported, measured model limits; no silent provider/model switching, open-ended retry, forced reasoning toggle, speculative performance PASS or extra model pass solely for parsing. Reconcile F2's 48-**entry** check against the real F3 48-**operation** cap: Gate creation embeds its Criteria, so do not treat every Criterion as a separate native staging call. Keep real per-Gate Criterion limits and staged operation/byte checks.

**Scoped manual correction:** [c12-map-markers](../tasks/c12-map-markers/README.md) contains exactly three standalone prompts: M1 parser, M2 model-generation integration/budget diagnostics, M3 one Codex Browser-only real-model dogfood-entry qualification. F1–F6 have been run; **do not rerun or rewrite them**. [F6's failed/interrupted closeout](../tasks/c12-rmr-man/fast/qualification/2026-11-03-f6-manual-closeout.md) remains NOT GREEN / DOGFOOD HOLD, including the recorded owner stop after an OS crash. Before any resumed live-model/browser attempt, confirm host stability and fresh owner authorization; this docs approval does not itself restart testing. No source implementation, tests, model change, version bump or qualification results follow from this decision.

# ADR 0048 — Engineering qualification ratings, evidence attribution, and safe progression

**Decision:** 2026-11-03 (America/Chicago). **Status:** OWNER-APPROVED FORWARD DESIGN / DOCUMENTATION ONLY. **Product:** Dope `0.12.7` reference; no code, runner behavior, version, prior qualification, or historical commit changed by this decision. **Contract:** [Engineering qualification and progression](../planning/p12/engineering-qualification-contract.md). **Proposed follow-on:** [c12-qualification-reporting](../tasks/c12-qualification-reporting/README.md).

## Context and observed defect

C12 Roadmap Sync made substantive progress but repeatedly reported a single **NOT GREEN** for very different conditions: a missing structural creation workflow, not-yet-observed browser cases, an environment-only Electron dependency error subsequently repaired, stale test source assertions, unrelated Work/Chat fixture failures, and an actual native revision-zero authoring gap. The P9 report demonstrated 93/93 focused tests, while two material owner-requested features remained incomplete. Neither broad-test failure nor green focused tests alone establishes the whole correction outcome.

Source inspection of `scripts/codex-phase-core.mjs` shows `detectCompletedPromptPrefix()` recognizes correction progress from reachable Git commit subjects. `scripts/codex-phase.mjs` validates process exit, package version and working tree, then writes the checkpoint and labels it passed; it does **not** independently establish that the agent's final response has qualified its required acceptance scope. A clean agent stop with no changes becomes a misleading “implementation completed but commit boundary failed.” A commit is an implementation checkpoint, not a qualification receipt.

## Decision

1. **Independent dimensions, never one overloaded enum.**
   - **Implementation:** `not-started`, `in-progress`, `partial`, `implemented`.
   - **Verification:** `not-assessed`, `qualified`, `scoped-qualified`, `evidence-gap`, `failed`, `blocked`; attach per-requirement case outcomes rather than hiding multiple different cases under one status. “Qualified” must be source-bound and scope-exact.
   - **Progression:** `continue`, `conditional`, `hold`, `stop` with an explicit reason, dependency ID, issuer and scope. A condition is not a waiver of the final contract.
   - **Failure attribution:** `introduced-regression`, `verified-pre-existing`, `flaky-or-environmental`, `obsolete-assertion`, `unattributed` with evidence and confidence. “Flaky” is not assumed from one rerun.
2. **GREEN remains a strict final gate.** A final GREEN means all mandatory acceptance requirements of a *declared, bounded qualification scope* are verified on the exact candidate, under stated environments, with explicit exclusions. `SCOPED GREEN` names the reduced scope and does not upgrade a broader Phase or native GUI. Final `NOT GREEN` remains appropriate when required features/tests are absent, but must state **partial implementation, failed behavior, or evidence gap** distinctly. Missing evidence never counts as PASS.
3. **Evidence-aware dependency checks.** A next task may continue when its *actual input/interface/safety prerequisite* is independently validated even if an unrelated UI or device matrix is left for a later explicit gate. Conditional continuation must list that bounded dependency, outstanding tests, assigned future gate and a real owner authorization when departing from a previously approved strict entry requirement. No implicit relaxation of the current prompt's contract.
4. **Hard stops remain absolute.** Unauthorized data writes, loss/corruption of canonical data, source hash/revision bypass, permission or secret leakage, forged/missing approvals, missing required dependency interfaces, fabricated evidence, and known unsafe destructive operations are STOP until repaired. No change of label or owner timing exception silently qualifies such a failure.
5. **Attributable failures only.** Compare product-wide test failures with a reproducible appropriate baseline and exact candidate. Track verified pre-existing and unrelated failures separately; investigate cleanup/host failures and stale source assertions. Unknown attribution remains unresolved. A broad suite failure cannot be automatically waived, nor can it automatically invalidate an unrelated scoped subsystem without determining relevance.
6. **Machine-readable qualification receipt, guarded by evidence.** Future runner records an immutable source/commit/version/bundle anchor, declared requirements, observed tests and environments, artifact hashes/references, per-case results, attribution, implementation/verification/progression states, blockers/deferred evidence, and actual reviewer/owner disposition. A model-authored “GREEN” sentence or marker commit is insufficient proof. Commit identity and qualification authority must be separate.
7. **Runner status and checkpoint semantics.** Display `implemented / qualification pending` when a commit exists but no verified qualifying receipt does. Render a safe no-change prerequisite stop as `BLOCKED`, not a commit failure; a clean implementation no-op uses an explicit justified outcome. A `--stop-after Pn` or equivalent must stop after the normal validated checkpoint without automatically starting Pn+1. Resuming must inspect the exact verified dependency and preserve prior Git/dirty-tree safety.
8. **Immutable history and transition.** Never rewrite prior P*.txt prompts that were run, past failure reports, success markers, or Git history to make earlier outcomes look better. New prospective assessments cross-reference previous evidence and distinguish historical runner “completed” counts from actual qualification. Existing runner stays under its present contract until a separate implementation and tests ship.
9. **Independent product Roadmap qualification.** Engineering prompt/correction statuses do not alter schema-2 Phase → Gate → Criterion GREEN, evidence/coverage approval, waivers, or source freshness. Neither AI staging nor an engineering implementation checkpoint can award Gate/Phase Green.

## Application to c12-roadmap-sync

P5 remains qualified only for its recorded scope; P6 is partially implemented (canvas creation/form parity outstanding); P7 is implemented with core history navigation browser-observed and remaining evidence gaps; P8 is source-scoped qualified; P9 is partially implemented because native revision-zero creation and canvas relationship/creation parity remain missing. The 715/721 suite failures and theme check must be attributed, not retroactively declared passing. P10 remains manual, unrun, and must still actually demonstrate a live complete one-request Roadmap and safety of selected approval, Markdown, and restore. These are forward classifications for communication, **not** retroactive amendment of original reports.

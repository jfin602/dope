# ADR 0042 — Chat reasoning lifecycle and diagnostic copy

**Decision:** 2026-10-31, owner-approved design. **Status:** ACCEPTED FOR FORWARD IMPLEMENTATION; DOCS ONLY / NOT IMPLEMENTED OR QUALIFIED. **Product version:** 0.12.7 unchanged. **Correction:** [c12-reasoning-streaming](../tasks/c12-reasoning-streaming/README.md). Earlier Chat/Pi/Planning/Work qualification remains historical.

## Problem

The one existing ChatPanel can render a long stream of Pi/local-model text as assistant output even while the run is incomplete. A cancelled turn may leave a long unfinished draft looking conversational; tool/debug activity and raw Planning JSON can swamp the transcript. A completed provider stream can incorrectly promote unclassified reasoning-like text into saved assistant content and future context. Users need live progress and durable inspection without making activity the canonical answer. They also want right-click Copy -> Copy with Reasoning on every Dope-owned Chat copy control, while ordinary left-click copy remains unchanged.

## Authoritative boundaries

1. **One turn, distinct channels.** Associate ordered, typed activity events (provider-exposed reasoning/thinking, provisional/unclassified text, sanitized tool/progress metadata) and an authoritative final answer with the same existing Chat ID, assistant message ID and execution ID. Terminal status is complete, failed, cancelled or interrupted as actually observed. Do not create a second Chat, Pi agent loop, Roadmap store or History owner.
2. **Classification must be evidenced, never guessed.** Prefer explicit Pi/provider thinking and final/text events; optionally recognize correctly delimited model-specific think blocks only when explicitly enabled and tested. Repetition, length, markdown, or apparent introspection alone do not prove reasoning. A model/provider without exposed reasoning displays **Provisional output** or **Activity**, not invented private thoughts. Provider-internal/hidden reasoning unavailable to Dope remains unavailable for display/export.
3. **Streaming is not commitment.** Show activity live in a muted, height-limited scroll area. Recognized answer deltas may preview, but only a successful provider completion commits a formal final assistant answer. On cancel/failure/no completion, retain captured provisional output for diagnostic inspection and export; show **No final response** rather than repackaging it as a completed answer. Preserve authentic typed Planning outcomes and clearly separate unvalidated raw Planning output.
4. **Context isolation is server-side.** Future prompt history, saved-Chat retrieval, automatic title, model routing, Roadmap intent, Planning validation, and Chat context summaries must derive assistant conversational history only from successfully completed, classified final answer content. Existing complete-status history gating remains; also prevent reasoning, cancelled drafts, diagnostics and raw tool events from being indexed, searched or injected as assistant speech through other paths. Do not alter Roadmap ownership/Markdown content or implicit grant behavior.
5. **Persistent inspection, bounded.** Retain typed, project-bound, execution-ID-bound activity separately from final answer content, through restart/reopen/retry, with explicit limits (target <= 128 KiB text and <= 512 event entries per execution; cap/redact raw tool details and report truncation). Store either in separate protected diagnostic records or an isolated validated execution-activity field whose every reader excludes it from context. Do not write unclassified activity to normal assistant content on failure. Older chats without events must continue loading. Never store secret tokens, raw restricted-file bodies, reusable command approvals or private provider payloads in activity.
6. **Rendering lifecycle.** Active turn: muted activity container visible and updated as events arrive, capped/virtualized so runaway streams do not bloat the Chat. Successful completion: activity auto-collapses under a compact **Reasoning / Activity** disclosure and formal final answer becomes the primary message. Failure/cancellation: collapsible activity plus truthful terminal status and **no fabricated final answer**. User may reopen at any time; preserve manual expansion choice during ordinary rerenders. Keep existing ChatPanel docking, readable markdown, selection, touch, drag-to-scroll and bounded update rate.
7. **Copy semantics.** Left-click of an existing Copy button retains that button's original payload (Copy Response is clean final, Copy Transcript is clean chronological conversation, Copy JSON remains explicit raw JSON). Right-click on **every Dope-owned ChatPanel/associated Chat or Work transcript Copy control** opens a common accessible anchored menu offering **Copy with Reasoning** for that control's scope. No permanent arrow/button. Keyboard Context Menu / Shift+F10 opens the same menu, arrows navigate, Escape dismisses; do not intercept native editor/OS Copy. If the target has no captured reasoning, show unavailable/disabled with a truthful reason; do not fabricate it.
8. **Diagnostic export.** Copy Response with Reasoning includes that turn's sanitized ordered activity, cancellation/failure status and any committed answer; Copy Transcript with Reasoning includes chronological user and assistant turns, per-turn recorded activity, and a labelled lack of final output where applicable. The action must preserve accessible captured reasoning faithfully, not summarize it or silently truncate; represent any storage/export limits explicitly. Never include credentials, raw private tool outputs or approval tokens. Copying has **zero** effect on chat context, stored status, model or Roadmap.
9. **Compatibility and ownership.** Reuse existing chatResponseCopyText/chatTranscriptCopyText behavior as clean default; create one shared scoped copy-with-reasoning formatter and context-menu handler. Preserve provider-independent Chat, Pi broker permission boundaries, source refs, Work candidates and independently operated native Electron.

## Design/test consequence

The relevant source seams are packages/pi-runtime/worker.mjs, pi-runtime-host.ts, pi-conversation-runtime.ts, ChatBackend, packages/chat service/schema/repository, ChatPanelController, chat-panel-presentation.ts, chat-panel-widget.ts and chat-context-composer.ts. The currently observed Pi worker streams text_delta but does not yet expose a separate thinking channel; avoid claiming local Qwen has one. The backend currently accumulates deltas as output, while normal context composition already filters to completed assistant messages. Qualification must exercise the missing distinctions explicitly.

**Mandatory replay:** A file-read request emits twelve near-identical reasoning/provisional paragraphs and is cancelled before completion. In Chat this is one bounded, labelled, inspectable activity record with no formal answer; ordinary copy/history/next-turn prompt omit those paragraphs, while right-click diagnostic copy reproduces available captured activity. Additional tests: successful reasoning/final separation, text-only/no-reasoning provider, tool interleave, split or malformed think delimiters, stale event/lease/retry, failure, restart, clean-versus-diagnostic copies, browser and owner-operated native Electron. Browser success never substitutes for native operation.

**Execution:** [c12-reasoning-streaming](../tasks/c12-reasoning-streaming/README.md) P1-P3 are compact runner prompts; P4 is separate **MANUAL Codex browser closeout**. Runner must stop before P4; no /activate, self-commit from prompts, version bump, automatic Run, fabricated qualification, Roadmap changes, or historical result rewriting.
